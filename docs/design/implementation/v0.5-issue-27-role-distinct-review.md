# v0.5 Issue #27 — Role-distinct Review Implementation

Status: implemented; role-distinct runtime acceptance pending

## Final behavior

### Core command and concurrency

- The App and CLI review command contains `CommandId`, incident identity, `ExpectedState`, `ExpectedSequence`, decision, reason, and evidence identities. It has no client-supplied `OccurredUtc`.
- Core maps the request to the Domain command and assigns `OccurredUtc` with its injected `TimeProvider` at execution time. Capability `ObservedUtc` is only a capability-observation input.
- `ExpectedState` and `ExpectedSequence` are one atomic optimistic-concurrency precondition. Core reads the current incident, resolves authority, validates the transition, appends the audit event, links evidence, and advances the incident inside one immediate SQLite transaction.
- An exact command retry returns the immutable event. Reusing the command ID with changed expected state, expected sequence, identity, decision, reason, or evidence fails closed. A retry after a later event returns the current incident without republishing the older decision as current.

### Role provenance and durable audit

- Core maps only the exact Project Manager role and the explicit Leader-role allowlist. Viewer role text, button metadata, and caller-supplied role names are not authority.
- `assignment_actor_role_history` is the immutable source of role observations. `assignment_current_actor_roles` is a guarded latest-observation projection: its insert/update must match the latest history tuple and delete is rejected. Core validates the projection and its provenance before capability evaluation and mutation.
- Schema v4 stores immutable incident, incident-evidence, audit-event, and audit-evidence records. Review-event triggers enforce current authority, latest role provenance, subject/reviewer inequality, next sequence, valid transition, and immutable incident advancement.
- Incident registration stores canonical immutable `registration_json`. The `compliance_review_incident_evidence_validate_insert` trigger uses SQLite `json_each` to reject links not declared by that registration; reads require the JSON, normalized scalar projection, and relational evidence links to agree. An exact registration retry validates the complete existing review history before returning. The `compliance_review_event_evidence_validate_insert` trigger applies the same membership rule to immutable event `audit_json`. Before appending a next sequence, Core validates the complete prior event history, including all evidence links, so tampered history blocks the append.
- On the Core-owned SQLite connection, `herdrops_review_audit_valid` recalculates the UTF-8 SHA-256 of `audit_json`, deserializes and domain-validates the event, and compares all persisted scalar columns with the JSON/domain event. Reads repeat JSON-hash, domain, scalar, evidence-link, and audit-replay validation.

### IPC, identity, and deadlines

- App and CLI use the dedicated current-user review-command Named Pipe and protocol v1. The server requires an App/App or CLI/CLI hello source/role pair and one correlated operation per client.
- After connection, each client binds the server to the OS-reported PID from `GetNamedPipeServerProcessId` and validates `HerdrOps.Core.exe`, `OriginalFilename=HerdrOps.Core.dll`, `ProductName=HerdrOps.Core`, executable SHA-256, process start time, file length, last-write time, and file stability across hashing. The server obtains the connected client PID with `GetNamedPipeClientProcessId` and binds the claimed reviewer pane to the admitted Herdr shell/foreground process tree.
- Windows ancestry authorization holds limited-information process handles for every member of the candidate-to-root chain, obtains creation times with `GetProcessTimes`, confirms processes remain running, and recaptures every parent relationship while all identities remain held. The recaptured chain must match the original traversal, and every parent creation time must be strictly earlier than its child creation time. Inaccessible, exited, reused, reparented, unstable, cyclic, incomplete, equal-time, time-inverted, or over-depth chains fail closed. This proves operational identity continuity and correlation only. A sufficiently privileged same-user process may forge parentage with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`, so the check is not cryptographic provenance, signing, or an unforgeable parent relationship.
- After the bounded handshake, one operation deadline begins before reading the operation frame and spans that read, client-process authorization, capability or mutation execution, and the response write without reset. Synchronous server delegates run behind a four-slot budget; a timeout releases the client slot but retains the delegate permit and cancellation source until the underlying task really completes, with late faults observed. Server shutdown waits for all tracked detached delegates before completing. Workflow and compliance-store monitor waits recheck cancellation every bounded interval. Compliance SQLite commands use a one-second command, provider, and `PRAGMA busy_timeout` lock-wait ceiling and register the operation token to request `SqliteCommand.Cancel`; provider failures become structured Core-unavailable responses. The cancellation request is cooperative and does not guarantee immediate interruption of a provider busy wait. Transaction acquisition and work already executing synchronously cannot be promised immediate cancellation or rollback.
- App and CLI create fresh linked deadlines for connect plus server-process validation, handshake, and operation phases; no hello is sent before validation succeeds. Synchronous validators run as isolated long-running tasks behind process-wide budgets of four for the App and two for the CLI. Waiting for a permit consumes the same phase deadline, and each permit is retained until its validator actually finishes. This bounds client calls and retained workers even though the validators themselves cannot be force-cancelled. Late faults are observed. An internal phase deadline becomes `TimeoutException`; caller cancellation remains `OperationCanceledException`.
- The CLI dispatcher routes `review` to `ComplianceReviewCliCommand` before the self-report routes. Review input derives the reviewer from `HERDR_PANE_ID`, requires `HERDR_ENV=1`, and rejects a public review-pipe override.

### App and presentation behavior

- Core capability results are authoritative for the selected incident. Review actions stay disabled until current role, current incident state, current incident sequence, allowed decision, and non-empty reason all match.
- The Queue uses capability and command request generations, a per-incident authoritative generation, selected incident identity, expected state and sequence, an atomic single-flight command guard, pending-command, and disposal guards. Every different same-incident replacement or sequence advance increments the authoritative generation. A late rejected result cannot update status after that generation changes; a late accepted result is recognized only for the exact next generation whose last audit-event ID equals the originating command ID. Selection accepts only a visible incident.
- `ComplianceReviewStateHub` validates the incident and audit Domain contracts, rejects immutable-registration and same-sequence conflicts, suppresses duplicate notifications, and exposes one accepted state change to the App. It invokes subscribers independently; nonfatal subscriber failures are logged with the exception type only, later subscribers continue to receive the change, and the accepted state is not replayed twice.
- Before publication, the command coordinator binds the response incident to the request incident. An accepted result must additionally bind the audit-event ID to `CommandId` and match the exact reviewer, decision, previous state, next sequence, reason, evidence identities, task, subject, result state, and audit hash. A later current incident returned by an exact already-present retry is allowed without presenting the older audit as its current decision. Rejected results carry status, code, and message only; they do not carry or publish an incident snapshot because the request lacks the immutable registration tuple needed to bind one safely. After a valid accepted response is received, the coordinator publishes it through the UI dispatcher without using caller cancellation for that publication. Caller cancellation remains effective while transport is waiting for a response.
- Queue status is localized and polite for pending, ready, accepted, already-accepted, canceled, stale, unauthorized, and unavailable outcomes. Status text does not grant authority.
- The shared state change updates both the live Compliance Queue and Widget. The Widget creates route `compliance-review:{incidentId}`; the application router selects the incident, navigates to `compliance-queue`, and activates the main window, failing closed when the exact target is unavailable.

### Language behavior

- Thai and English are complete separate UI modes. Only one selected language is rendered at a time. Technical identifiers such as actor IDs, incident IDs, task IDs, route values, protocol names, and hashes remain unchanged.

## Runtime successor boundary

The implementation gate does not create or control Herdr panes. A fresh runtime successor must use distinct, already-running Project Manager, Leader, and incident-subject panes from a standard, non-elevated Herdr pane; admit their exact pane IDs and assignment roles; register one incident; execute Project Manager → Leader → Project Manager decisions; and bind the resulting database audit hashes to the exact Herdr runtime report.

The runtime report must explicitly retain the same-user limitation: Named Pipe isolation, server PID/image/hash checks, and process ancestry are operational attestation, not cryptographic publisher authentication, code-signing proof, or cryptographic process/server authentication. A sufficiently privileged same-user process may forge parentage with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`, and Herdr protocol 19 supplies pane root PIDs without creation identities, so a root PID recycled before Core starts its held-process snapshot cannot be distinguished cryptographically. A deliberate same-user database writer can also register or spoof its own SQLite validation function. These remain trust-boundary residuals. Any runtime run that injects another pane ID, cannot prove the exact connected client PID is in that pane's currently observed process tree, or cannot bind accepted SQLite audit hashes to the admitted Herdr observations receives no role-distinct runtime credit.

The legacy single-process runtime wrapper is deliberately disabled. Changing
`HERDR_PANE_ID` in one orchestrator cannot prove role-distinct action
authorship. Its blocker is the first executable statement after `param`, so
call and dot-source forms cannot change caller preferences/strict mode or load
the orchestration helper. The replacement must be distributed across the three admitted
panes and bind server-observed PID/start/ancestry receipts to one run nonce
and one exact non-empty server instance before any report can claim Runtime
evidence. The retained ancestry hash is recalculated from the canonical
observed PID/start chain, and the receipt hash is recalculated from the exact
canonical receipt payload with only the receipt-hash field excluded. These are
deterministic Contract/Synthetic integrity checks, not Actual Herdr Runtime or
cryptographic publisher-authentication credit. An ancestry chain additionally
requires strictly increasing parent-to-child creation FILETIMEs and unique PID
and PID/start identities; repeated-PID cycles fail closed.

## Evidence boundary

The implementation gate is Contract plus BuiltProcess Integration plus local SQLite Integration evidence. App rendering from deterministic inputs is Synthetic UI evidence. Static source and schema checks do not become runtime evidence. No actual Herdr runtime credit is claimed until the review flow is captured from a standard, non-elevated Herdr pane and the connected process identities, role observations, Core responses, and immutable audit hashes are independently bound in one fresh runtime record. Independent Review and Release evidence remain separate.
