# v0.4 distributed role provenance (Issues #22 and #23)

## Status

The previous runtime harness is fail-closed. One orchestrator process generated all lifecycle JSON and supplied both `actorId` and `actorRole`; observing four terminal IDs elsewhere in the same Herdr snapshot did not bind any submission to those pane processes. That topology cannot earn Runtime evidence.

## Required production protocol

1. Core creates an unpredictable run nonce and a unique server instance ID. Both are scoped to one bounded acceptance run.
2. The operator deposits only an action request in each target pane. The CLI process running inside that pane reads its own `HERDR_PANE_ID`; the request payload cannot supply an actor or role.
3. Core obtains the named-pipe client PID with `GetNamedPipeClientProcessId`, holds the process identity, and records its creation time.
4. Core asks the admitted, exact Herdr server for that pane's root process and verifies a complete held PID/start-time ancestry chain from the CLI client to that root. Inaccessible, exited, reused, reparented, cyclic, equal-time, inverted-time, or changed chains fail closed.
5. Core derives actor identity from the admitted pane and authorizes the role from the exact current Herdr Agent observation plus the acceptance action plan. It ignores/rejects any client role claim.
6. Core hashes the canonical submission and atomically consumes `(run nonce, action ID, sequence)`. Duplicate, out-of-order, prior-run, or other-server messages fail closed.
7. Only Core emits the receipt consumed by `V04DistributedRoleProvenancePolicy.ps1`. The receipt includes a canonical `core-` server instance, non-empty run nonce, action/sequence, derived actor, authorized role, canonical submission hash, client PID/start FILETIME, pane-root PID/start FILETIME, and the successful ancestry result. Integer and Boolean fields must retain their native JSON types; numeric or Boolean strings are rejected.

The acceptance topology is closed: exactly four receipts are required in exact sequence—Project Manager `assignment`, Backend Leader `delegation`, Backend Worker `handoff`, and Reviewer `acknowledgement`. Actor IDs, client PID/start identities, and pane-root PID/start identities must each be four-way distinct; client PIDs cannot be reused across roots, and a client PID must differ from its pane-root PID even when their start FILETIMEs differ. Receipt and action-plan schemas reject both missing and additional properties; arbitrary roles or action names are not extensibility points in this acceptance contract.

The existing `HerdrReviewClientProcessAuthorizer` and `WindowsProcessAncestryReader` provide a starting point, but the self-report server and service do not yet invoke them. Wiring them requires changes to the C# protocol, CLI client, server, Core service admission, persistence/replay rules, and integration tests; a PowerShell wrapper alone cannot establish this trust boundary.

## Evidence boundary

`Test-V04DistributedRoleProvenance.Tests.ps1` is Contract plus Synthetic evidence only. It verifies fail-closed policy behavior for wrong-pane, role-spoof, PID/start mismatch, cross-run, and replayed receipts. It does not observe an installed Herdr instance, real pane ancestry, actual distinct Agents, Runtime acceptance, or Release readiness.
