# v0.7 Issue #40 UAT/release-gate preparation

Status: preparation only. This slice does not perform a session action, install,
clean-machine run, Runtime acceptance, Release publication, human approval, or
issue closure.

## Input and exact candidate binding

`tools/Test-V07ReleaseGate.ps1` consumes an operator-created JSON input and an
evidence root. The input must contain exactly one dependency manifest for each
of Issues #35, #36, #37, #38, and #39. The tool reads each manifest and every
listed evidence file from the supplied root, checks containment and reparse
status, bounds the bytes, rejects duplicate/unknown JSON properties, and
recomputes every SHA-256 at invocation time.

The candidate is never a value embedded in this policy or its fixtures. Before
validation the tool resolves both values from the checkout:

```powershell
git rev-parse HEAD
git rev-parse HEAD^{tree}
```

The supplied lowercase commit and tree must match those exact values and the
checkout must be clean. A rebuilt artifact, changed tree, changed dependency
manifest, or changed evidence byte therefore requires a new input and a new
run. The committed templates contain placeholders only; they are not evidence.

Example invocation from a clean candidate checkout:

```powershell
$repo = 'Z:\HerdrOps'
$root = Join-Path $repo 'artifacts\release-gates\v0.7.0\issue-40'
pwsh -NoProfile -File "$repo\tools\Test-V07ReleaseGate.ps1" `
  -DependencyEvidencePath "$root\dependency-evidence.json" `
  -EvidenceRoot $root
```

`-HumanUatPath` is an optional validation input. If supplied, it must be a
separate human-created record with `decision: ACCEPTED`, a non-placeholder
signature, signer, role, and UTC date bound to the same commit/tree. The tool
does not create that record and does not copy those human fields into its
report.

## Automation and evidence boundary

The generated report always has `status: PENDING`. Its human decision fields
remain `PENDING`; automation never emits `APPROVED`, a signer, or a release
go/no-go decision. A successful invocation means only that the supplied
Static input and synthetic validation checks passed. It does not turn any
dependency into Runtime/Release credit.

The gate deliberately keeps these boundaries explicit:

| Evidence class | This preparation slice |
|---|---|
| Static | Candidate identity, schema, bounds, hashes, containment, reparse and policy checks |
| Synthetic | Hostile selftests and temporary dynamic fixtures |
| Contract | Not observed |
| Runtime | Not observed / not claimed |
| Human UAT | Pending / not observed |
| Release | Not observed / not claimed |

Run hostile selftests in both supported Windows shells:

```powershell
pwsh -NoProfile -File .\tools\Test-V07ReleaseGate.ps1 -SelfTest
powershell -NoProfile -File .\tools\Test-V07ReleaseGate.ps1 -SelfTest
```

The selftests create and remove only a uniquely named temporary child. They
bind synthetic manifests to the current committed HEAD at test time, so no
WIP commit/tree/hash is stored in source.

## History-preserving successor rule

Final rebase, squash, or replacement of an accepted candidate is forbidden.
When the final Issue #39 successor is available, integrate it with a
history-preserving `git merge --no-ff`, then regenerate every candidate and
dependency binding from the resulting exact `HEAD` and `HEAD^{tree}` and repeat
the independent review. A regenerated input is required even if only the
source commit changed and the product bytes appear otherwise equivalent.

This preparation branch does not push, merge into `main`, tag, publish, close
an issue, or claim Runtime/Release.
