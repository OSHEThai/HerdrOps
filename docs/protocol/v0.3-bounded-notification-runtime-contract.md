# HerdrOps v0.3 bounded notification runtime contract

Status: implementation contract for GitHub Issue #16. This document does not admit actual Herdr runtime evidence or close the v0.3 release gate.

## Accepted input

The notification center accepts only an `ActivityPipelineStep` whose disposition is `AcceptedImmediate` or `AcceptedBuffered`. Rejected and duplicate pipeline steps cannot create history rows or popup requests. The notification identity is the normalized activity event identity SHA-256; no raw payload is retained.

The retained event fields are limited to:

- normalized source event and event type identifiers;
- correlation, Agent terminal, and Task identifiers;
- urgency and UTC occurrence/observation timestamps;
- the activity contract's already-redacted summary;
- acknowledgement and presentation state.

The widget flattens newlines and tabs and limits the displayed summary to 180 characters. The bounded history retains the normalized redacted summary, never an unredacted source payload.

## Bounds and flood control

Default limits are fixed and testable:

| Collection or behavior | Default bound |
| --- | ---: |
| Individual notification history | 128 |
| Remembered exact identities | 512 |
| Visible groups | 32 |
| Remembered urgent-presentation groups | 512 |
| Urgent popup suppression window per group | 30 seconds |
| Notification Widget rows | 4 |

A group is derived deterministically from the debounce key when supplied, then event type, Agent, Task, and a correlation fallback. The group identifier is SHA-256, so an internal grouping key is not displayed. The first unique High or Critical event in a group requests immediate presentation. Further unique urgent events in that group during the suppression window increase the group count without requesting another popup. Exact identity repeats never request presentation.

History, identity memory, visible groups, and presentation memory are bounded independently. Eviction counters remain observable. Eviction permits later re-admission after the declared memory horizon; it is not represented as global or durable deduplication.

## Acknowledgement

Acknowledgement is monotonic for each retained item. Acknowledging a visible group marks every currently retained item in that group and preserves the first acknowledgement timestamp. A later unique event in the same group is unacknowledged and does not rewrite prior acknowledgement evidence.

The v0.3 implementation keeps this state in process memory. Disk persistence across App restarts is not implemented or claimed.

## Deep-link rules

Each activity-backed widget row carries the exact source event identifier, event identity SHA-256, correlation identifier, optional Agent terminal identifier, and optional Task identifier.

Routing fails closed:

1. Open the exact Realtime Activity event only when its source event identifier, correlation identifier, and event identity SHA-256 all match the page state.
2. Otherwise open Agent Detail only when the exact terminal identifier exists in the admitted state.
3. Do not silently select a different event or Agent.
4. The separate “view all” action may open the Realtime Activity page without claiming a selected event.

## Language and accessibility

Thai and English interface labels come from separate catalog values. A language change rebuilds group labels, severity labels, acknowledgement text, and automation names. Source identifiers and source-provided redacted summaries remain data rather than translated interface copy.

Every actionable notification row is keyboard focusable and has a localized automation name. The acknowledgement button has a separate localized automation name. Notification history and Agent Detail actions are exposed as explicit buttons.

## Authorized runtime command

Run from an authorized Herdr pane:

```powershell
dotnet src\HerdrOps.Core\bin\Release\net10.0-windows\HerdrOps.Core.dll trace-herdr-notification-runtime `
  --report artifacts/runtime-evidence/v0.3.0/issue-16/notification-runtime.json `
  --seconds 120
```

The command fails closed unless `HERDR_ENV=1`, performs no session control, and binds the monitor connection to the admitted executable SHA-256. It does not synthesize activity: it subscribes to the admitted session's own accepted `pane.agent_status_changed` transitions, and only when a transition resolves to a live pane with a known Herdr Terminal identifier does it build one `ActivityEventEnvelope` per transition, route it through the product's real `ActivityEventPipeline`, and hand the resulting `ActivityPipelineStep` to a real `NotificationCenter`. Each retained transition record binds the admitted session's own reported event count, ingest sequence, and connection epoch alongside the transition's occurrence and observation timestamps. Runtime acceptance requires all of these report fields:

- `evidenceClassification = "Runtime"`
- `runtimeObserved = true`
- `notificationDeliveryObserved = true`
- `herdrAgentCorrelationObserved = true`
- `sessionControlInvoked = false`
- at least one transition whose `notificationDisposition` is `Added` or `Grouped` and whose `agentTerminalId` is non-null

This command captures Agent-only correlation; the accepted Agent-status event carries no Task identifier, so `taskId` is never populated on these notifications.

## Evidence classes

- Unit and integration tests prove deterministic grouping, exact deduplication, collection bounds, acknowledgement, projection bounds, and exact routing identifiers.
- WPF runtime tests prove actual control rendering and interaction against contract-backed synthetic activity and state.
- The committed reference image binds visual intent only.
- The authorized runtime command proves actual Herdr Agent-status event delivery through the real pipeline and notification center, with Agent correlation, for one admitted session.
- Actual end-to-end notification latency, Task correlation, restart behavior, and end-to-end secret-redaction observations against live terminal bytes remain pending and must not be inferred from this implementation evidence.
