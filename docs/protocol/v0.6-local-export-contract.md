# HerdrOps v0.6 Local Export Contract — Issue #33

Status: implementation contract; actual Herdr Runtime and v0.6 release acceptance are not claimed

## Purpose and scope

Issue #33 defines a local export of the accepted Evaluation and Daily Summary
query snapshot. The export is one bounded three-file set: strict machine-readable
JSON, human-readable Markdown, and tabular CSV. All three documents represent the
same normalized snapshot and carry the same export identity, source snapshot hash,
generation timestamp, and version metadata.

The exporter serializes the snapshot supplied by the accepted query/UI boundary.
It does not reread Herdr, SQLite, raw evidence, terminal output, or arbitrary files
while writing the report. A later query or runtime change therefore cannot silently
change one report after the snapshot has been accepted.

This contract covers report shape, provenance, redaction, bounds, atomic local
writing, reproducibility, and fail-closed acceptance. It does not authorize a
reviewer, change a score, mutate a Daily Summary, collect new evidence, or publish
data remotely.

## Export identity and source binding

Every export has one normalized source snapshot with these required values:

- `exportContractVersion`, which must equal `1`;
- a non-empty `exportId` and a UTC `generatedUtc` timestamp;
- `sourceSnapshotSha256`, the SHA-256 of the canonical accepted Evaluation/Daily
  Summary query snapshot;
- the scoring formula version and formula SHA-256 when Evaluation data is present;
- the source/query contract versions for every included report section; and
- a complete, sorted source-reference set for every displayed value that claims
  provenance.

The source snapshot is canonicalized as strict UTF-8 JSON with case-sensitive
camel-case names, no comments, no trailing commas, invariant numeric formatting,
UTC timestamps, normalized ordering, and no unknown members. Hash comparison is
case-insensitive hexadecimal comparison over exactly 64 characters. A report must
carry the exact source hash that the accepted query/UI snapshot supplied; the
exporter must not invent a replacement hash.

Evaluation values retain the scoring contract's formula version, formula hash,
input-snapshot hash, result hash, dimension, source slot, provenance identity,
and evidence identity. A missing or incomplete score remains explicitly missing
or incomplete with a null total; export must never turn it into zero, a passing
value, or an omitted row.

Daily Summary values retain the deterministic local-day boundary, workstream,
aggregation/source version, and sorted source-event/evidence identities used to
produce each number, highlight, issue, action, timeline item, or recommendation.
The export may omit a value only when the accepted snapshot marks it unavailable
and the report states the reason.

## Report formats and bounds

The JSON report is the machine-readable authority for exported values. Markdown
is its human-readable projection and CSV is its bounded tabular projection;
neither is a second source of truth. Each report includes the export identity,
section version, generation time, source snapshot hash, formula/source versions,
values, explicit missing-data states, and provenance references.

The following bounds are part of version 1:

| Item | Maximum |
| --- | ---: |
| Complete JSON + Markdown + CSV set | 4 MiB |
| Evaluation records | 10,000 |
| Daily Summary records | 10,000 |
| Source references per displayed value | 512 |
| Source-reference entries across the export | 20,000 |
| Human-readable text field | 8,192 UTF-8 bytes |

The exporter rejects a request or serialized report that exceeds any bound. It
does not truncate, paginate, silently drop records, replace text with an inferred
summary, or switch to an unrequested format. Numeric values, timestamps, hashes,
identities, and null states must remain lossless within the contract.

## Redaction and local destination policy

Only allowlisted report fields from the accepted snapshot may be serialized.
Exported provenance uses stable identifiers and hashes, not raw artifact bytes,
terminal payloads, credentials, tokens, cookies, authorization headers, secrets,
or arbitrary command lines. Managed evidence paths and external source references
are not exported unless the accepted policy has already converted them to an
approved redacted reference. Machine names, user-profile paths, and environment
secrets are not report fields.

The exporter treats all human-readable summaries and references as untrusted
input. Control characters, invalid UTF-8, embedded report delimiters, unapproved
secret material, unsafe paths, or a failed redaction precondition reject the
whole export. Redaction is not allowed to change a hash-bound value while leaving
the original provenance hash in place: a transformed value must carry its own
approved redaction state and corresponding hash, or the export fails closed.

The destination must be a local filesystem path selected for this export. Relative
paths, parent segments, device paths, UNC/network paths, filesystem roots,
reparse-point directory components, and an existing destination collision are
rejected. The exporter stages all three reports in the destination directory,
flushes, rereads, hashes, and validates every complete file, then publishes the
set without overwriting an existing export. A failure before set publication leaves no accepted final
report; a stale staging file is not an export and must not be treated as one.

## Fail-closed rules

The exporter rejects the request and produces no accepted report set when any of
the following occurs:

- the snapshot is absent, malformed, out of contract, internally inconsistent, or
  has a source hash mismatch;
- formula, source/query version, result, evidence, or provenance identity is
  missing, malformed, duplicated, or inconsistent with the displayed value;
- an incomplete or unavailable value is represented as a pass, zero, current
  success, or an unexplained omission;
- a source reference cannot be resolved to the accepted snapshot's sorted source
  set, or an evidence identity/hash does not match its retained metadata;
- a redaction check, size bound, timestamp rule, local-destination rule, UTF-8
  check, canonical serialization check, flush, validation, or atomic publication
  step fails; or
- any report would contain a value, field, or section not present in the
  accepted snapshot.

The failure is observable through a structured rejection reason suitable for
Contract evidence. The exporter must not publish a partial set, reuse a prior
successful set, downgrade to a weaker validation mode, or claim that a rejected
export was generated.

## Acceptance contract

Issue #33 is accepted only when the implementation demonstrates all of the
following against deterministic fixtures and contract checks:

1. JSON, Markdown, and CSV values match one accepted query/UI snapshot, including
   null/incomplete states and exact source snapshot hash.
2. Evaluation exports retain formula version/hash, input and result hashes,
   source-slot separation, and evidence/provenance identities.
3. Daily Summary exports retain deterministic day/workstream metadata and a
   complete source set for every displayed aggregate or explainable item.
4. Repeated exports from identical canonical bytes and a fixed `generatedUtc`
   produce byte-identical reports and identical report hashes. A changed snapshot,
   formula, source set, or generation time produces a changed bound value or hash.
5. Secret, credential, raw-payload, unsafe-path, invalid-UTF-8, and unapproved
   reference fixtures never appear in either report.
6. Oversized, malformed, mismatched, incomplete-without-state, duplicate, or
   publication-failure fixtures fail closed without a final partial report.
7. The destination and all three report formats remain local, bounded, and atomic;
   no network publication or remote side effect occurs.

## Evidence boundary

Static evidence covers document/schema parsing, canonical field order, bounds,
redaction rules, and exact source/contract hashes. Synthetic evidence covers
fixture snapshots, deterministic Evaluation/Daily Summary projections, redaction
cases, missing/invalid values, and repeated fixed-clock exports. Contract evidence
covers source-hash binding, formula/source version binding, provenance identity
checks, strict JSON/Markdown/CSV set behavior, atomic local publication, and
fail-closed rejection results.

These evidence classes can support Issue #33 implementation acceptance only. They
do not prove an installed Herdr session, actual Herdr events, production evidence
admission, role authority, live runtime behavior, clean-machine installation,
packaging, independent human acceptance, or v0.6 release readiness. Actual Herdr
Runtime and Release evidence are **NOT OBSERVED** by this contract.
