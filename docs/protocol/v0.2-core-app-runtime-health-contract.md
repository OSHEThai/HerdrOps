# v0.2 Core-to-App Runtime Health Contract — Issues #7, #9 and #10

Status: protocol v2 implementation and automated evidence complete; actual Herdr composite runtime
gate pending

## Purpose

Core connectivity and Herdr connectivity are different facts. A healthy per-user Core process can
remain available while the upstream Herdr process is starting, reconnecting or stopped. Protocol
v2 carries those facts separately so Dashboard and Widget surfaces never present persisted Agent
state as currently live merely because the App pipe still works.

## Wire behavior

- Pipe name prefix: `herdrops-state-v2-`, followed by the current-user SID hash.
- Authorization: both endpoints require `.NET PipeOptions.CurrentUserOnly`.
- Initial message: protocol-v2 App hello at sequence zero.
- Snapshot: normalized Herdr state plus the current runtime-health record.
- State delta: contiguous, hash-bound state change plus the current runtime-health record.
- Health update: a `runtime-health` message that preserves the current state sequence.
- Bounds: strict JSON inside the existing four-byte little-endian length-prefixed frame, up to 4 MiB.

The runtime-health record contains status, transition time, last accepted state time, and
bootstrap/event/disconnect/reconciliation counters. A standalone health message also carries the
SHA-256 of the normalized state it describes. Exact Herdr server PID/start/path/hash identity stays
in the Core runtime trace, where the composite gate verifies it against the admitted executable.

## Validation and fail-closed rules

The App rejects:

- an unknown health status;
- a non-UTC timestamp;
- a negative counter;
- `Connected` without a successful bootstrap and accepted-state timestamp;
- a state/hash mismatch;
- a malformed or out-of-order state message.

Only `Connected` means Herdr is live. `Starting`, `Reconnecting` and `Stopped` preserve last-known
identity and topology for diagnosis but make current Agent counts unknown and Agent statuses
offline. A Core pipe interruption is rendered separately from an upstream Herdr interruption.

## Composite runtime evidence

Run from a fresh, unmoved, standard, non-elevated pane in the dedicated Herdr Named Session `acceptance`.
`HERDR_ENV=1`, `HERDR_PANE_ID`, and `HERDR_SOCKET_PATH` identify that surviving control
session. Pass the different `default`-session Agent Lab socket as the monitored target:

```powershell
# Replace both values with the separately approved final candidate identities.
$expectedSourceCommit = '<approved-source-commit>'
$expectedSourceTree = '<approved-source-tree>'
$targetAgentLabSocket = Join-Path $env:APPDATA 'herdr\herdr.sock'
./tools/Test-V02LiveRuntimeAcceptance.ps1 `
    -TargetHerdrSocketPath $targetAgentLabSocket `
    -ExpectedSourceCommit $expectedSourceCommit `
    -ExpectedSourceTree $expectedSourceTree `
    -Language Thai `
    -DurationSeconds 600
```

The expected commit and tree are operator-supplied identities for the approved
candidate. The gate rejects a mismatch or dirty checkout before and after the
run and records both identities in the evidence report.

The control and target socket paths and observed server PID/start identities must differ. Stopping a Herdr server terminates every pane
process in that session, so a gate running in the target session could not survive the required
restart. The script enumerates named sessions before starting the run and requires the control socket
to belong to the running `acceptance` session; the target socket must belong to a different running
session. It then verifies the active control pane, binds the gate process to its ancestor control
server, and fails closed if the sockets or control/target server identities match.

The script does not invoke Herdr session control. The user creates Event A through a genuine
Agent-status transition in the target Agent Lab. After Dashboard closure, the user stops and
restarts only the target session, waits until the Floating Vertical Widget is `LIVE`, and creates
Event B through a second genuine Agent-status transition. Focus, workspace, tab, and pane topology
changes receive no Event credit. Each phase baseline is hash-chained before observation and accepts
exactly one Event-count increment in the same epoch, with stable bootstrap/disconnect counters. The
accepted ordering is either the direct Event sequence or exactly one unlabelled connected snapshot
reconciliation followed by the Event sequence; each sequence may perform at most one authoritative
reconciliation. Core labels the matching transition's `AcceptedEventKind` as exact
`pane.agent_status_changed` only after successful connected reconciliation and records the accepted
workspace, pane and status so the independent gate can bind it to the App's same-pane change; consumed frames
that enter reconnecting/failure paths remain unlabelled and do not set Core `EventObserved`. Core records exact admitted
Herdr identities, normalized state hashes, Agent-topology hashes, and Agent status/state-sequence hashes.
Aggregate identity strictness is intentional: every connected evidence transition must carry
`AllAgentsHaveLiveIdentity=true`. An empty Agent set, blank Agent kind or name, `Unknown` status,
or any other non-live Agent state fails closed and cannot earn accepted Event evidence. This strictness is aggregate and intentional.
The topology hash must remain unchanged, exactly one Agent state-change sequence must advance by one,
and the optional leading snapshot's Agent status-state hash must equal either the phase baseline or the
accepted Event state. This rejects added/removed/moved Agents, collapsed status changes, and unrelated
Agent-status transitions while still allowing a presentation-only poll before the Event. The production App records the hashes rendered by
Overview, Live Organization, Agent Detail, Compact Widget, Normal Widget and Floating Vertical
Widget before and after Dashboard closure. The gate accepts the WPF evidence only when all App
state hashes occur in the Core trace.

The target Agent must use a current official Herdr integration and report a native resumable session
reference before Event A. After the replacement server appears, Core waits for at most ten seconds
for the same Agent kind and name to resume in every prior pane before it publishes the replacement
bootstrap as `Connected`. The new terminal identity is expected after a full server restart. Snapshots
captured while those Agents are still absent consume no epoch, bootstrap, Event, disconnect or
reconciliation credit. If the grace period expires, ordinary monitoring may accept the observed
snapshot, but the missing or changed Agent topology cannot satisfy Event B or receive Runtime credit.

Runtime credit also requires exact phase order in the Core transitions: Event A, a later target
transport disconnect, a later connected snapshot from a replacement target PID/start identity, and
then Event B from that replacement process. A reconnect to the same process, an earlier unrelated
restart after the initial connected baseline but before Event A, or an Event B observed before
replacement fails closed. The Acceptance control server PID
and start time must remain unchanged through the run.
