# v0.7 State Recovery Contract

Status: implementation contract for the migration, backup, rollback, and corrupted-state quarantine slice of GitHub Issue #37.

This contract is local-only and does not require an installed Herdr instance. It does not claim Herdr Runtime or Release evidence.

## Scope and evidence boundary

The recovery path is owned by `SqliteHerdrStateStore` and the files under `Storage/Recovery/`. The Core command
`restore-state-store` reaches `StateStoreRecoveryService`; App and the standalone self-report CLI do not open
SQLite directly.

The implementation and focused tests classify evidence as:

| Class | Meaning in this contract |
|---|---|
| Static | Source-level path, naming, JSON trace, and fail-closed policy checks |
| Synthetic | Fault-injected migration interruption and local damaged-file replay |
| Contract | SQLite identity, `quick_check`, `integrity_check`, `user_version`, and byte-hash assertions |

Every recovery trace carries all three classifications so that a report cannot be mistaken for an installed-product observation. `ActualHerdrRuntime` is always `NOT_OBSERVED`, and `Release` is always `NOT_OBSERVED` in this slice.

## Database admission

1. The database path must be absolute, local to a Windows volume, and free of traversal segments, reserved device names, alternate data streams, invalid filename components, and trailing dot/space ambiguity.
2. The parent directory is created one component at a time. Existing directory components and the database file are rejected when they are reparse points, including a dangling leaf link whose ordinary existence probe is false. The ownership lock's parent and leaf are checked before the lock is opened. Recovery directories are checked again after creation.
   These checks are best-effort point-in-time checks against accidental or non-adversarial changes. They do not
   provide a no-follow primitive or claim protection against a local adversary racing a filesystem operation.
3. A missing database is the only path that may be initialized by SQLite. An existing zero-byte file, truncated file, non-SQLite file, or SQLite identity/integrity failure is corruption and fails closed.
4. SQLite `PRAGMA database_list` must identify the expected `main` file. `PRAGMA user_version`, `PRAGMA schema_version`, `PRAGMA quick_check`, and `PRAGMA integrity_check` are used at the relevant admission and recovery boundaries.

The store never changes a damaged primary into a new empty database. The damaged primary is retained in place while a quarantined byte-identical copy is created for diagnosis and recovery.

## Migration transaction and backup protocol

For an existing valid database whose schema is behind the supported version:

1. The fault-injection seam may stop at `BeforeBackup`. No backup is created and the primary remains byte-identical.
2. Before any migration SQL runs, the store creates a SQLite backup under the sibling `backups` directory. The backup is written through a temporary file and atomically renamed to a collision-free `.bak` name.
3. The backup is independently checked with SQLite primitives and identified by byte length and SHA-256. A `MigrationBackup` trace is written under the sibling `recovery` directory.
4. The fault-injection seam may stop at `AfterBackup` or `BeforeMigration`. The recoverable backup remains present and the primary is not reset.
5. Each forward migration runs in one SQLite transaction. The seam may stop at `AfterMigrationBeforeCommit`; disposal of the uncommitted transaction rolls back all schema, history, and `user_version` changes.
6. `AfterMigrationCommit` is observable after the safe commit boundary. If a process stops there, the committed schema is valid and the pre-upgrade backup remains available for explicit rollback.

Existing migration names, SQL, history hashes, and forward-only behavior remain unchanged.

## Explicit backup rollback

The recovery seam accepts only a backup below the database's sibling `backups` directory. The backup must have a valid SQLite header and pass `quick_check`, `integrity_check`, and identity validation before it is considered restorable.

Rollback copies the backup to a same-directory temporary file, validates that temporary file, and then hashes both the staged copy and the named source against the expected source identity immediately before the atomic replace/move. The expected destination identity is rechecked at that same boundary. If a primary exists, the replaced bytes are retained as a collision-free `.prior.bak` artifact. The replacement is validated again after the atomic operation; a failed postcondition restores the prior bytes or removes a newly installed destination when the original was absent. Cleanup failures remain attached to the primary failure. A `BackupRestore` trace records both byte identities only after the operation succeeds.

Rollback is not an automatic silent reset. It is an explicit recovery operation with a named backup input and a
post-recovery SQLite check. The production-reachable Core command requires all of the following before it can
replace a destination:

```text
restore-state-store
  --database <absolute destination>
  --backup <absolute direct child of destination\..\backups>
  --expected-backup-sha256 <64 hex characters>
  --expected-database-sha256 <64 hex characters|ABSENT>
  --confirm RESTORE_STATE_STORE
```

The command acquires the destination ownership lock, rechecks both identities, validates the source with SQLite,
performs the atomic replacement, and validates the restored destination again. A changed identity, missing
confirmation, active ownership lock, invalid source, or failed postcondition rejects the operation closed. The
command reports only path tokens and hashes; it does not print full source, destination, trace, or prior-file paths.

## Corrupted-state quarantine

When pre-migration admission fails with a corruption classification, the store creates a unique directory under the sibling `quarantine` directory:

```text
<database>.corrupt.<utc-stamp>.<token>.<attempt>/
  <database>
  <database>-wal       (when present)
  <database>-shm       (when present)
  metadata.json
  recovery-trace.json
```

The primary and any SQLite sidecars are copied with bounded streaming I/O and their length/hash identities are recorded. The original primary remains at its original path; this prevents a later startup from interpreting a moved-away damaged file as permission to initialize a new store.

Quarantine uses a staging directory and an atomic directory move. A pre-existing target is never opened, overwritten, or populated. Collision attempts advance the suffix and preserve the earlier quarantine unchanged.

Metadata and trace include the failure phase, sanitized failure type/message, schema version when known, source file
identities, `Static|Synthetic|Contract` classification, and explicit `NOT_OBSERVED` Runtime/Release boundaries.
Full recovery paths are never serialized: path and artifact fields use deterministic non-reversible tokens, and
exception messages pass through the centralized diagnostic redactor. Cleanup failures are attached to the original
exception as sanitized context; the primary exception remains authoritative and unreclaimed artifacts remain
available as evidence.

## Deterministic verification

`StateStoreRecoveryTests` covers:

- interruption before backup;
- interruption after backup and byte-identifiable trace evidence;
- transaction rollback at a safe migration boundary;
- explicit backup restore with post-recovery SQLite integrity checks;
- damaged primary quarantine without silent reset;
- quarantine name collision without overwriting a prior quarantine;
- existing zero-byte state rejection; and
- traversal-path rejection before file operations.
- diagnostic redaction for prose credentials, headers, Bearer/JWT/PEM values, configured variants, and local paths;
- bounded configured-secret work and allocation;
- recovery trace/quarantine path tokenization and failure-message redaction;
- cleanup failure preservation with retained temporary evidence; and
- production Core restore-command reachability, confirmation, source/destination identity preconditions, staged/source
  TOCTOU rejection, post-restore rollback for present and absent destinations, ownership-lock reparse rejection, and
  post-restore validation.

These tests are local SQLite Integration evidence with Static/Synthetic/Contract classifications. They are not actual Herdr Runtime, independent review, packaged Release, clean-machine, or UAT evidence.
