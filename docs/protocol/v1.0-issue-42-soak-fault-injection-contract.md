# HerdrOps v1.0 Issue #42 24-Hour Soak and Fault-Injection Contract

Status: bounded preparation contract for GitHub Issue #42. This document defines the
precise 24-hour soak, fault-injection, database-integrity, alert-consistency, restart,
and provenance rules that the fail-closed harness must enforce. It does not run a soak,
restart any process, or close Issue #42. The harness reports `PENDING` in preparation
mode and never emits a soak `PASS`.

## Purpose and authority

Issue #42 is `V100-02`: prove the exact v1 release candidate remains accurate and
recoverable during sustained actual-Herdr operation. `Plan/` remains the product and
release-planning authority, and `Plan/RELEASE-GATES.md` remains the version-gate truth.

The gate is fail-closed. A missing file, missing contract marker, failed deterministic
self-test, changed commit, dirty checkout, byte mismatch, invalid database probe,
inconsistent alert, unauthorized restart, unbounded telemetry, or a claimed soak `PASS`
without observed Runtime and Release evidence is a failure or a refused `PASS`.

## Evidence boundary

| Class | This slice may observe | This slice does not prove |
|---|---|---|
| Static | Exact repository files, contract/document markers, parseable PowerShell, SHA-256 identities | Runtime behavior of any process |
| Synthetic | Deterministic fixtures, bounded filesystem replay, simulated event/alert/database-probe inputs | Compatibility with installed Herdr or a real 24-hour run |
| Contract | Versioned restart-authorization, database-integrity-probe, and telemetry/bound rules | End-to-end sustained operation |
| Runtime | `NOT OBSERVED` | Actual 24-hour soak, real Herdr/Core/App process control, fault-injection against a live instance |
| Release | `NOT OBSERVED` | Exact packaged candidate-byte acceptance, clean-machine operation, publication |

The harness never starts Herdr, Core, or App, never opens a live database, and never
reports a soak `PASS` from preparation work. Runtime and Release evidence remain
`NOT OBSERVED / NOT CLAIMED`.

## Candidate admission

1. The soak must run against the exact packaged candidate bytes. The archive, its
   content manifest, and its installed-file set each receive a SHA-256 identity.
2. Admission is a single, exact binding of `(archiveSha256, archiveBytes, sourceCommit)`
   to one run. A missing archive, a byte-count mismatch, or a SHA-256 mismatch fails
   closed and invalidates the run.
3. Any rebuild produces a different SHA-256 and therefore invalidates the run: a rebuilt
   candidate requires a new, complete 24-hour run. An unchanged candidate whose bytes
   are re-hashed identically may continue.

## 24-hour soak definition

The soak is exactly 24 hours (86,400 seconds) of actual-Herdr operation against the
exact candidate bytes. The run records an elapsed-time and completion flag that are both
`0` and `false` in preparation mode. A soak that terminates before 24 hours of actual
operation is incomplete and cannot `PASS`.

## Fault-injection scenarios

The fixed scenario set is:

- `FI-01` Herdr disconnect — sever the named-pipe/socket endpoint.
- `FI-02` Herdr reconnect — restore the endpoint and reconcile from a fresh snapshot.
- `FI-03` Core process restart — stop and restart Core under explicit authorization.
- `FI-04` App process restart — stop and restart App under explicit authorization.
- `FI-05` Sequence gap — drop an event and force snapshot reconciliation instead of silent continuation.
- `FI-06` Concurrent reconnect during snapshot — reconcile without duplicate or orphan state.

Each scenario must conclude with zero unhandled crashes and zero unreconciled states.

## Database integrity assertion

The harness consumes a database-integrity probe, never the raw database. A probe is the
ordered set of SQLite observations the product's store already exposes:

- `PRAGMA quick_check` returning exactly `ok` (case-insensitive);
- `PRAGMA integrity_check` returning exactly `ok` (case-insensitive);
- `PRAGMA user_version` within the accepted forward-only set (`{1,2,3,4}` for v1);
- `PRAGMA database_list` identifying the expected `main` file.

Any probe value outside these bounds fails closed. A missing database, a missing probe,
or a probe that was not actually observed is reported `NOT OBSERVED`, never `ok`. The
byte identity of the database is asserted separately by an exact SHA-256 binding at the
admission boundary.

## Alert consistency definition

Given the ordered event set and the alert set produced during the soak, every alert must
satisfy all of:

1. The alert has a unique `id`.
2. The alert references exactly one existing event `id`.
3. The alert `agentId` equals the referenced event `agentId`.
4. The event `id` set has no duplicates.
5. The alert `acknowledged` flag is paired with an `acknowledgementTime` if and only if
   it is `true`.

Any orphan alert, duplicate identifier, agent mismatch, or inconsistent acknowledgement
is an alert-consistency failure and fails closed.

## Restart authorization model

Herdr, Core, and App restarts are never automatic and never silent. Each restart of
`Herdr`, `Core`, or `App` requires an explicit operator authorization token equal to
`SOAK_RESTART` for that specific component, and a recorded restart action. In preparation
mode every restart request is refused with `NOT PERFORMED`, and no process is controlled.

The production-reachable Core restore path already uses an equivalent explicit
confirmation (`restore-state-store --confirm RESTORE_STATE_STORE`); this soak harness
extends the same principle to the soak-time restart actions and records them as bounded,
hash-bound provenance rather than as automatic recovery.

## Bounded telemetry and hash provenance

Telemetry is bounded. Every artifact obeys hard limits on total artifact count, bytes per
artifact, lines per artifact, entries per artifact, and path length. Exceeding any limit
fails closed.

Provenance is a SHA-256 chain over the ordered artifacts: each link hashes the previous
link plus the artifact name plus the artifact SHA-256. The final link is the run's
provenance root. Only hashes, bounded counters, and sanitized failure messages are
collected; raw terminal, process, or database bytes are not.

## Fail-closed result model

`Get-SoakVerdict` computes exactly one of `PASS`, `PENDING`, or `FAIL`:

- Any failed check, invalid byte, invalid probe, inconsistent alert, unauthorized
  restart, or unbounded artifact is `FAIL`.
- In preparation mode the verdict is always `PENDING`, even when every preparation check
  succeeds, because Runtime and Release evidence are `NOT OBSERVED / NOT CLAIMED`.
- `PASS` requires every check to pass, preparation mode to be off, and both Runtime and
  Release evidence to be observed.

The harness therefore refuses `PASS` in synthetic/preparation mode by construction.

## Deterministic self-test contract

The self-tests exercise every policy function against deterministic inputs with no live
process, listener, or database access:

- SHA-256 text and file hashing with a known empty-string vector;
- bounded-telemetry pass and over-limit fail-closed cases;
- alert consistency pass, orphan, duplicate, and acknowledgement-inconsistency cases;
- candidate-byte admission with exact and tampered SHA-256/byte cases;
- database-integrity probe with `ok`/`ok`/`4`/`main`, a corrupted `quick_check`, and a
  future `user_version` out of the accepted set;
- restart authorization refusal in preparation mode, refusal with an empty or mismatched
  token, and authorization with the exact token outside preparation mode;
- verdict matrix proving preparation mode never returns `PASS`;
- deterministic provenance chain against a known vector.

Self-test evidence is Static, Synthetic, and Contract only. It is not Runtime or Release
evidence.
