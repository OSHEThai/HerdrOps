# v0.3 Bounded Terminal and Windows Process Contract — Issue #14

## Status

Implementation contract for GitHub Issue #14. Contract, synthetic, and local Windows-process evidence can pass outside Herdr. The issue remains open until an authorized Herdr pane produces both an actual bounded pane-read trace and an actual Herdr-PID-to-Windows-process correlation trace.

## Terminal read boundary

HerdrOps admits one terminal operation: `pane.read` with all of these fixed fields:

- `source`: `recent_unwrapped`
- `format`: `text`
- `strip_ansi`: `true`
- `lines`: required integer from 1 through 200
- `pane_id`: required explicit pane identifier

There is no HerdrOps API that accepts a missing line limit or lets a caller select `visible`, `recent`, `detection`, ANSI output, or an unbounded source. Pane revisions drive reads. A successfully read revision is not read again; failures can retry only after the configured interval. A pane that advances while the bounded request is in flight can return the newer revision without losing the read result.

The protocol response must correlate the request identifier and requested pane, must report `recent_unwrapped` plus `text`, and cannot exceed 256 KiB of strict UTF-8 text. The collector then applies control-character normalization, secret redaction, a 1,024-character and 4-KiB UTF-8 summary limit, and deterministic hashes before producing an activity event or trace record. Raw terminal text is never a property of those persisted records.

## Secret handling

Before persistence, terminal and command summaries redact these bounded patterns:

- token, secret, password, private-key, connection-string, and API-key assignments;
- Basic and Bearer authorization values;
- URI user-info credentials, with or without a separate password;
- known GitHub classic, fine-grained `github_pat_`, GitHub App, and OpenAI token shapes;
- JSON Web Tokens.

Regex evaluation uses a one-second defensive timeout and the non-backtracking engine. The timeout is a fail-closed safety ceiling, not a latency target; it includes enough scheduling tolerance for contended Windows runners. Input and output byte limits are explicit. Truncation is Unicode-rune safe. The raw payload is hashed transiently for correlation; only hashes and redacted text leave the sanitizer.

## Windows process correlation boundary

HerdrOps requests `pane.process_info` with an explicit pane identifier. It samples only shell or foreground PIDs returned by that response. It never enumerates unrelated Windows processes to invent a pane association.

Each live identity is `PID + process start UTC`. This prevents PID reuse from inheriting a prior CPU baseline. A sample records:

- pane and Herdr-reported source (`Shell` or `Foreground`);
- PID, process start UTC, and bounded process names;
- total-CPU delta normalized by elapsed time and logical processor count;
- working-set and private-memory bytes;
- hash and redacted form of reported command metadata;
- observation and expiration UTC.

The first CPU sample has no percentage. Counter regression also resets the percentage. Telemetry expires after 15 seconds by default, uses a bounded identity table, and deterministically evicts its oldest identity at capacity. Read failures expose stable failure codes without retaining operating-system exception text.

## Collector and activity pipeline

`HerdrTerminalProcessCollector` runs only when the admitted monitor snapshot is `Connected`. It sorts pane IDs, inspects no more than 256 panes per cycle by default, debounces terminal and process requests independently, sanitizes before entering the activity pipeline, and records only bounded trace DTOs. Terminal events are `Observed`; Windows process events are `Correlated`. Both use deterministic IDs and bounded debounce keys.

The monitor and pane inspector use separate exact-hash-verifying API clients. This prevents concurrent pane inspection from overwriting the monitor's connection identity while the discovery/subscription/authoritative-snapshot bootstrap is being validated.

## Authorized runtime command

Run from an authorized Herdr pane:

```powershell
dotnet artifacts/bin/HerdrOps.Core/release/HerdrOps.Core.dll trace-herdr-terminal-process `
  --report artifacts/runtime-evidence/v0.3.0/issue-14/terminal-process.json `
  --seconds 120 `
  --interval-ms 500 `
  --lines 80
```

The command fails closed unless `HERDR_ENV=1`, performs no session control, binds both monitor and inspection connections to the admitted executable SHA-256, and reports zero unbounded read attempts by construction. Runtime acceptance requires all of these report fields:

- `evidenceClassification = Runtime`
- `runtimeObserved = true`
- `paneReadObserved = true`
- `processCorrelationObserved = true`
- `sessionControlInvoked = false`
- `unboundedTerminalReadAttemptCount = 0`
- at least one terminal preview and one process telemetry record

## Evidence boundary

- Unit tests prove redaction, Unicode-safe bounds, revision/debounce behavior, and bounded planner state.
- Contract tests prove the exact JSON request/response shape.
- Named-pipe integration tests prove the serialized request always carries a non-null line bound.
- Collector and telemetry tests use deterministic Herdr response fixtures and include one actual Windows sample of the test process.
- None of those tests proves that an installed Herdr server returned terminal bytes or that a PID from a real Herdr pane correlated with Windows.
- Only the authorized runtime command can provide the two missing runtime traces. Until they are captured and independently reviewed, Issue #14 and the v0.3 release gate remain open.
