# HerdrOps v0.7 lifecycle contract

Status: bounded non-runtime implementation slice for GitHub Issue #36.

This contract covers the desktop lifecycle seams that can be implemented without
an installed Herdr instance or an OS-level acceptance run: current-user settings
composition, notification-area command routing, the WPF tray adapter, and
current-user start-at-logon registration. Settings remain the versioned input
contract in `docs/protocol/v0.7-settings-contract.md`.

## Evidence boundary

- Contract: injectable interfaces, menu invariants, command routing, reversible
  settings snapshots, per-user single-instance ownership, dashboard/widget
  lifecycle, current-user Run-key identity, quoted executable command,
  idempotence, and fail-closed path validation.
- Static: source, project, parse, build, and format checks.
- Synthetic: in-memory tray and startup backends; no OS resource is created.
- Integration: language/menu projection and lifecycle behavior using in-memory
  fakes and temporary test data only.
- Actual Herdr runtime: NOT OBSERVED.
- Actual notification-area visibility: NOT OBSERVED.
- Actual Registry Run mutation: NOT OBSERVED.
- Actual Startup-folder mutation: NOT OBSERVED.
- Live AppData read/write: NOT OBSERVED.
- Human accessibility and reference-host acceptance: NOT OBSERVED.
- Release/package/clean-machine evidence: NOT OBSERVED.

The validation commands for this slice do not start `HerdrOps.App`, construct
`SystemTrayBackend`, construct `WindowsCurrentUserRunBackend`, or use the real
settings destination. Tests use an in-memory backend for every OS-facing
interface and temporary or in-memory data for settings tests. The production
composition is the only route that creates `JsonAppSettingsStore` at
`%LOCALAPPDATA%\HerdrOps\settings\appsettings.json` and pairs it with
`WindowsCurrentUserRunBackend`.

## Tray contract

`TrayMenuModel` is immutable and rejects duplicate commands or a menu that does
not contain exactly two language commands with exactly one checked item. The
selected language is either Thai or English; the model cannot represent both
selected or neither selected. `TrayCommandRouter` maps the lifecycle commands
to an injected target:

- show/open the existing Dashboard;
- hide the existing Dashboard without closing it;
- show the admitted configured widget variant;
- enable or disable the configured widget through persisted settings;
- select Thai;
- select English;
- exit the application cleanly.

`TrayLifecycleController` does not create an OS resource in its constructor.
Only `Start` calls the injected backend. `Start`, `Refresh`, `Stop`, and
`Dispose` are safe to repeat at the controller boundary. Target and backend
exceptions are not silently swallowed.

The production adapter uses the Windows built-in `System.Windows.Forms.NotifyIcon`
surface from the WPF application and has no third-party package dependency. The
approved overview crop is converted from the screenshot matte to transparent
premultiplied pixels, then scaled from the logical 16-pixel size to a bounded
system-DPI size. Its HICON/OS icon is hidden during shutdown and the context
menu is disposed. Alpha conversion and DPI sizing are covered synthetically;
HICON creation and actual tray visibility remain NOT OBSERVED.

The tray exposes a minimal user-operable route for opening the configured widget,
enabling or disabling it, showing or hiding the Dashboard, selecting exactly one
language, toggling start-at-logon, and exiting. Dashboard language buttons,
widget-gallery selection, and tray widget enablement are all routed through the
lifecycle controller and saved through the injected `IAppSettingsStore`; a saved
snapshot can be restored or reset. The Dashboard close action is close-to-tray in
normal composition, while a shutdown close is explicit. An actually closed
Dashboard reference is discarded and the next restore creates a fresh window;
repeated show/hide/restore calls are idempotent. The production Overview/gallery
uses the shared widget launcher, so widget windows are keyed by variant, reused
while alive, discarded on close, and recreated on a later open. Start-at-logon is an OS-owned
current-user Run setting rather than a field added to the existing settings JSON
schema, and the controller preserves a conflicting value instead of overwriting
or deleting it.

## Single-instance and normal startup

Normal startup constructs an injected per-user process-wide gate and registers
its cleanup with the startup transaction before attempting acquisition.
Production uses a SID-scoped named mutex in the Windows Global namespace. A
second launch disposes the non-owning gate before the transaction commits and
exits without exposing a Dashboard. If acquisition throws and disposal also
throws, rollback preserves the acquisition exception as primary and reports the
disposal exception as ordered cleanup evidence. The gate lease is idempotent;
failed disposal remains retryable only through the owning transaction until a
successful retry clears the pending action. Tests use an in-memory
implementation and do not create the production mutex.

Composition, settings load and startup-status read, widget application, tray
start, and Dashboard exposure are one startup transaction. The shared widget
launcher is composed before the settings applier is invoked. The Dashboard is
created hidden and is not exposed until the preceding stages succeed. A fault
at any stage rolls back acquired resources in reverse order. If a primary
startup fault and rollback fault both occur, the primary exception is first and
the ordered cleanup exception is second; failed cleanup actions remain
retryable where the underlying resource permits it.

## Start-at-logon contract

The production backend is restricted to:

```text
HKCU\Software\Microsoft\Windows\CurrentVersion\Run
```

It never opens `HKLM`, never writes the Startup folder, and does not require
administrator elevation. The deterministic value name is `HerdrOps`. The stored
command is exactly one quoted, fully qualified local `.exe` path, for example:

```text
"C:\Program Files\HerdrOps\HerdrOps.App.exe"
```

The path validator accepts only a traditional local-drive absolute path whose
first three characters are `X:\` or `X:/`; UNC, device, extended, `\??\`,
relative, drive-relative, and other namespaces are unsupported. Every remaining
component is checked before normalization. Empty components, traversal,
wildcards (`?` and `*`), quotes, control characters, invalid Windows
characters, colons outside the drive separator, alternate data streams,
trailing spaces or dots, and Windows reserved device names are rejected. This
includes names before an extension such as `CON.exe`, `COM1.bin.exe`, and
`LPT9.exe`, as well as malformed extended/device paths. The resulting Run value
is exactly one pair of quotes around the normalized executable path; embedded
quotes are rejected, so no ambiguous command-line escaping is emitted. File
existence is intentionally not asserted by this contract; installation/package
validation owns that later concern.

`StartAtLogonService.Enable` writes only when the deterministic value is absent
and is a no-op when it already equals the expected quoted command. A different
command is a `Conflicting` state and causes `Enable` to fail closed without
writing. Enable and disable operations enter a per-user cross-process
coordination primitive, then re-read immediately before and after mutation. This is the strongest
available boundary for the Registry value: Windows Registry value APIs do not
provide a compare-and-swap/set-if-absent primitive. A foreign writer that does
not honor the mutex can still race after the recheck; the contract therefore
does not claim absolute atomicity against uncooperative external writers.
`Disable` removes only the exact expected command; it is a no-op for an absent or
conflicting value. `GetStatus` returns `Disabled`, `Enabled`, or `Conflicting`.
The conflict tray item is disabled and a programmatic conflict toggle is a
status-preserving no-op, so a click never throws for that state. Backend
failures and malformed input remain explicit exceptions.

## Application composition and shutdown

`AppLifecycleController.InitializeAsync` loads the current-user settings
snapshot, creates defaults only when no document exists, applies the admitted
language, and reads the startup status through the injected service. User
changes use the existing settings store's `SaveAsync`, `RestoreAsync`, and
`ResetToDefaultsAsync` APIs. The WPF composition supplies the real current-user
store, `WindowsCurrentUserRunBackend`, and the existing widget launcher; tests
supply fakes and never reach Registry or live AppData.

Shutdown actions are named and run in tray, Dashboard/widget, runtime,
single-instance, and base-application order. Every action is attempted even
when an earlier action fails. All failures are reported together as
`ShutdownCleanupException` with the original exceptions preserved. Tray
cleanup retains an undisposed controller when backend disposal fails so a later
cleanup pass can retry it. Notification, theme, and retention settings have no user-facing
controls in this slice and are explicitly deferred to a later Issue #36 slice;
they are not represented as completed work here.

## Deferred evidence

This slice does not claim that a real tray icon is visible, that Windows will
launch the packaged executable at logon, that an actual Registry value has been
mutated, that the Startup folder is unchanged on a reference host, or that a
human can operate the menu with assistive technology. Those require separately
authorized runtime, human, and release evidence.
