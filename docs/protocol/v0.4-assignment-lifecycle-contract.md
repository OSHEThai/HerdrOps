# HerdrOps v0.4 assignment lifecycle and provenance contract

Issue: [#19](https://github.com/OSHEThai/HerdrOps/issues/19)

## Scope

This contract defines the durable version 1 lifecycle projection created from a
Core-accepted self-report. It represents assignment, acknowledgement, delegation,
progress, deviation, evidence, and handoff events without replacing historical
provenance when current task or role state changes.

This is a technical protocol contract and uses one stable English vocabulary. It does
not define Dashboard or Widget copy. User-facing Thai and English catalogs remain
separate.

## Acceptance boundary

`HerdrOpsAssignmentLifecycleMapper` is the only mapping from
`HerdrOpsAcceptedSelfReport` to `AssignmentLifecycleEvent`. It preserves the Core-owned
sequence, acceptance time, source, correlation identifier, submission hash, event
identifier, task identifier, actor identity, event-specific fields, and parent identity.
The mapper recomputes the strict submission hash and rejects an accepted record whose
hash does not bind the submission bytes.

The lifecycle contract accepts only:

- contract version `1`;
- source `HerdrOps.Core`;
- positive Core sequence;
- non-empty event and correlation identifiers;
- non-default UTC occurrence and acceptance timestamps;
- an acceptance timestamp that does not precede occurrence;
- strict event-specific fields and SHA-256 values;
- bounded identifiers and text with no control characters.

## Deterministic transitions

| Event | Required prior state | Result |
| --- | --- | --- |
| Assignment | No existing task | Creates the immutable Assignment Contract and current task |
| Acknowledgement | Assigned, Delegated, or HandedOff | Confirms the current assignee and role |
| Delegation | Acknowledged or active acknowledged state | Changes the current assignee and records a relationship |
| Progress | Acknowledged or active acknowledged state | Advances non-regressing progress |
| Deviation | Acknowledged or active acknowledged state | Increments the deviation count |
| Evidence | Acknowledged or active acknowledged state | Increments the evidence count |
| Handoff | Active state with at least one evidence event | Changes the assignee and records the review handoff |

Every non-assignment event must name the applied current lineage tip as its parent and
must be submitted by the current assignee. A delegation or handoff target must
acknowledge before acting.

## Audit dispositions

Consumed events are append-only and receive one deterministic audit disposition:

- `Applied`
- `SequenceGap`
- `OrphanTask`
- `OrphanParent`
- `InvalidTransition`
- `DuplicateHandoff`

An identical retry, event-identity conflict, sequence conflict, or sequence regression
does not consume another sequence in the reducer. A byte-identical persistence retry
returns the original stored event. A different event at an existing persisted sequence
or event identifier fails closed.

Rejected consumed events remain queryable but cannot mutate the current task, role, or
relationship projections. Sequence gaps remain visible and establish the next expected
Core sequence.

## Provenance hashes

The domain uses separate canonical SHA-256 identities for:

- normalized lifecycle events;
- Assignment Contract task snapshots;
- assignment, delegation, and handoff relationships;
- actor-role observations and current-role projections;
- lifecycle audit entries;
- complete replay results.

Each audit entry binds the event hash, disposition, code, acceptance time, prior task
state hash, and result task state hash. The SQLite transaction verifies that the prior
hash matches the persisted task and that the proposed step exactly matches the store's
deterministic reducer before accepting it. This prevents a valid-looking step produced
from a disconnected reducer history or forged disposition from replacing current state.

## SQLite schema version 2

Schema version 2 adds:

- `assignment_lifecycle_events`: append-only event and audit ledger;
- `assignment_tasks`: current task and Assignment Contract projection;
- `assignment_relationships`: append-only assignment, delegation, and handoff edges;
- `assignment_actor_role_history`: append-only actor-role observations;
- `assignment_current_actor_roles`: current actor-role projection.

Foreign keys bind task, relationship, role, and event identities. Triggers reject
updates and deletes from every historical ledger. Strict table checks bound identifiers,
enum values, counters, sequence values, and hashes.

Opening a version 1 database performs an integrity check, validates the exact version 1
migration identity, creates a backup, applies only migration 2 in one transaction,
records its exact script hash, and validates the complete migration history. Existing
version 1 state events remain unchanged and queryable. A future schema fails closed.

## Query and restart behavior

The store exposes ordered lifecycle events, a current task by task identifier,
relationships by task, complete or actor-filtered role history, and validated current
roles. Reads recompute and validate JSON, scalar projections, canonical state, audit,
relationship, and role hashes.

After restart, replaying the ordered persisted event ledger must produce the same task,
relationships, role history, diagnostics, and replay result hash as the original replay.
The store restores and validates this reducer once at startup, advances it in constant
work for normal commits, rebuilds it after a failed database transaction, and reloads it
if the database sequence changes outside the owning store.
The committed fixture is bounded by `100000` events and includes a PM-to-Leader-to-
Worker-to-Review trace, one orphan, one deviation, evidence, and one duplicate handoff.

## Evidence boundary

Domain tests establish deterministic transition behavior. Migration and SQLite tests
establish local persistence, restart, append-only enforcement, and query behavior.
The committed replay fixture establishes deterministic synthetic evidence only. These
results do not prove an installed Herdr session, actual role-distinct agents, Delegation
Graph or Task Alignment rendering, independent review, v0.4 acceptance, or release
readiness.
