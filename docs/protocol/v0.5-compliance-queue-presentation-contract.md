## Reference hierarchy

The page preserves the shared HerdrOps shell and the reference hierarchy:

1. Four summary cards for suspected, confirmed, pending Leader review, and pending Project Manager review.
2. Severity, state, actor, task, and reviewer filters plus deterministic sort selection.
3. A dense incident queue with visible severity, actor, task, state, time, assigned reviewer labels, and a localized exact range/total/page footer whose disabled pagination controls have distinct automation names and help text.
4. A synchronized selected-incident panel with rule facts and evidence provenance.
5. A synchronized evidence list and four review-action affordances.

The named WPF regions are `ComplianceSummaryCardsRegion`, `ComplianceFiltersRegion`, `ComplianceIncidentTableRegion`, `ComplianceDetailsRegion`, `ComplianceEvidenceRegion`, and `ComplianceActionsRegion`.

## Presentation states and sorting

The presentation model keeps these states distinct: `Suspected`, `Confirmed`, `PendingLeader`, `PendingProjectManager`, and `Dismissed`. Severity labels remain distinct from workflow state labels and use separate semantic brushes.

Every filter is an exact presentation match over normalized fixture values. A filter or sort value outside its current catalog fails closed instead of silently selecting another behavior. Changing a filter or sort rebuilds the visible queue, preserves the selected incident when still visible, and otherwise selects the first visible incident or clears detail, evidence, and actions when no row remains. Severity sorting is deterministic from highest to lowest with newest observation as the tie-breaker; newest sorting uses UTC observation time with incident ID as the stable tie-breaker.

Selection is the single source for incident detail, evidence, and review actions. The UI must not retain detail from a row that is no longer selected or visible.

## Review-action authority boundary

The page presents `Confirm`, `Send to Leader`, `Escalate to Project Manager`, and `Dismiss` so the approved hierarchy and role requirements can be reviewed. The deterministic fixture can project Project Manager, Leader, and Observer applicability, but this metadata is not authorization. In the Issue #26 Synthetic/read-only surface every action is disabled. Each action exposes its required-role label and a localized unavailable reason through visible copy, a disabled-control tooltip, and UI Automation help text.

No command, click handler, state transition, database write, or review-audit append is allowed in Issue #26. A disabled presentation control is not authorization evidence.

## Localization and accessibility

Thai and English are separate complete modes backed by the shared catalog. A rendered surface contains copy from exactly one selected language; Agent names, task IDs, incident IDs, rule IDs, paths, hashes, and product names remain literal data. Catalog keys must have exact parity.

Filters use real `ComboBox` controls, the incident queue uses a real selectable control, and review actions use real `Button` controls. Focus remains visible, labels accompany color, disabled state is visually clear and readable, disabled tooltips are available, and automation names/help text are non-empty. At 1366×768 the review actions remain docked in the visible right panel while incident detail and evidence can scroll independently. The page must retain its hierarchy at 1672×941 and 1366×768.
