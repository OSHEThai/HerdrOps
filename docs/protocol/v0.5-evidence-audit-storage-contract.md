# v0.5 Evidence Metadata, Hashing, and Audit Storage Contract — Issue #25

Status: implementation and automated evidence complete; independent review pending

## Purpose and evidence boundary

This contract defines how HerdrOps records immutable evidence metadata, optional managed artifact bytes, append-only review history, and terminal retention events. It is the storage foundation for the later Compliance Queue and role-authorized review workflow.

The implementation provides Contract and local SQLite Integration evidence. It does not prove actual Herdr collection, role authority, privacy redaction against real data, Compliance Queue rendering, installed-product retention, or v0.5 release readiness.

Schema v3 is the immutable Issue #25 evidence foundation. Later forward-only schemas may extend the same database; Issue #27 adds review-authority ledgers in schema v4 without changing the v3 evidence identity, managed-byte, retention, or audit contracts. The Issue #25 gate therefore pins the v3-owned files and verifies that the current schema never regresses below v3 while reporting the observed forward schema separately.

## Evidence identity and metadata

Evidence contract version 1 records:

- Task ID, actor ID, source event ID, source, and an already-redacted source reference;
- UTC observed, ingested, and retain-until timestamps;
- explicit `Present` or `Missing` availability;
- explicit `ExternalReference` or `ManagedCopy` storage;
- content length and SHA-256 for present artifacts; and
- a separate metadata SHA-256.

The evidence identity uses a domain-separated, length-prefixed SHA-256 over the linkage, availability, content length, and content SHA-256. Changed bytes therefore produce a different identity even when every linkage field is unchanged. Observation, ingestion, retention, storage location, and managed relative path are metadata bound by a separate metadata SHA-256. A retry with the same identity but different immutable metadata fails closed instead of overwriting the original row.

A missing artifact is admitted only as explicit missing metadata. Its content length, content hash, and managed path remain null, and it cannot claim managed storage.

## Managed artifact vault

SQLite stores metadata and hashes, not artifact bytes. An optional managed copy is streamed once into a staging file while its SHA-256 and length are computed. The final object path is derived from the evidence identity and remains under the configured absolute evidence vault. Path traversal, absolute metadata paths, empty path segments, parent segments, reserved characters, filesystem/share roots, and reparse-point paths are rejected. Every existing directory component from the filesystem or share root through the vault and object path is inspected before use; a reparse point, inaccessible component, or non-directory ancestor fails closed.

Managed bytes are opened without writer sharing while captured. Reads require a confirmed regular non-reparse file, recompute its length and SHA-256, and fail closed on tampering, inaccessible objects, directory masquerades, or an incomplete retention operation. Existing immutable metadata is idempotent; a retry cannot restore an artifact whose retention event has already completed.

External artifacts are hashed during capture but are not copied or re-read by HerdrOps. Their continued availability remains the responsibility of the external source.

## SQLite schema v3

Forward-only migration `evidence-metadata-review-retention-audit` creates four ledgers:

1. `evidence_items` — immutable evidence metadata and canonical JSON/hash;
2. `review_audit_events` — immutable review events and per-case hash chain;
3. `review_audit_evidence` — immutable evidence links; and
4. `evidence_retention_events` — immutable terminal managed-byte retention events.

Every ledger rejects ordinary `UPDATE` and `DELETE` operations through SQLite triggers. Foreign keys bind review links and retention events to existing evidence metadata. Existing databases are integrity-checked and backed up before migration. Each migration and its history/version updates share one SQLite transaction; a forced failure after partial schema work rolls back the entire migration while preserving the prior version and backup.

## Review audit contract

Each review event has a caller-supplied non-empty GUID, review case, reviewer actor and role, action, state, reason, UTC occurrence time, sorted evidence identities, evidence-set SHA-256, previous-event SHA-256, and complete audit SHA-256.

The store assigns a contiguous per-case sequence and previous hash. A case must start with `Opened/Open`. Later events cannot reopen a case, regress time, skip sequence, or break the hash chain. Only `Closed/Closed` terminates the case, and ordinary appends after closure fail closed. Reusing an event GUID with exact content is idempotent; changed content is rejected.

These transitions preserve history but do not authorize a reviewer. Leader and Project Manager authorization, confirmation, dismissal, and escalation remain Issue #27.

## Retention behavior

Retention evaluates only present managed copies whose retain-until time is due and which do not already have a terminal retention event.

- If any linked review case is currently open, the artifact is protected and no terminal event is written.
- Once all linked reviews are closed, verified managed bytes are atomically moved within the vault to a deterministic pending-retention path. A hash-bound `Purged` event is committed before the pending bytes are deleted.
- If bytes are already absent, an explicit hash-bound `AlreadyMissing` event is appended.
- Evidence metadata, review history, evidence links, and retention history remain immutable after managed bytes are removed.

If the database write fails after the move, the verified pending bytes remain recoverable and ordinary reads fail closed. The next retention run either restores them when a linked review is open or completes the `Purged` audit and cleanup. If the audit committed before cleanup was interrupted, the next run validates the existing audit and removes the pending bytes. The evaluator remains idempotent after a terminal retention event. Full policy defaults, UI controls, real-data redaction, export behavior, and installed-product runtime acceptance remain Issue #28.
