# v0.5 Explainable Compliance Rule Engine Contract — Issue #24

Status: implementation and automated evidence complete; independent review pending

## Purpose and evidence boundary

This contract defines the deterministic compliance-policy foundation used by later v0.5 storage, review, and UI work. It evaluates four rule kinds from explicit normalized inputs:

1. scope violation;
2. missing evidence;
3. unapproved deviation; and
4. review-order violation.

The engine emits only `Suspected` findings. It has no transition that can confirm, dismiss, or otherwise mutate an incident. Those role-authorized actions remain in Issue #27. Evidence bytes, immutable audit storage, retention, redaction, Compliance Queue rendering, and actual role-distinct runtime acceptance remain in Issues #25–#28.

## Evaluation inputs

Every request supplies contract version, Task ID, actor ID, and bounded arrays of:

- assigned relative path prefixes;
- timestamped action targets and optional deviation IDs;
- deviation target prefixes, state, request time, and decision time;
- evidence requirements and admitted/non-admitted submissions; and
- sequenced review actions with reviewer identity and UTC time.

All identifiers are non-blank, unpadded Unicode Form C with no control characters. Paths are bounded project-relative Windows paths normalized to `/`; absolute, drive-qualified, empty-segment, `.` and `..` paths are rejected. Every supporting input ID is globally unique. Collections are bounded to 256 items and known finding identities are bounded to 256 exact SHA-256 values.

The structural contract rejects malformed enums, non-UTC timestamps, duplicate identities, impossible deviation timestamps, and unsafe paths. A semantic problem local to one rule remains observable as that rule's `Error` outcome while other rules continue evaluating. For example, a submission linked to an unknown requirement produces `orphan-evidence-submission`; it does not create or confirm an incident.

## Rule behavior

### Scope violation

An action is in scope only when its target equals an assigned prefix or begins with that prefix followed by `/`, using Windows case-insensitive comparison. This prevents `src/backend-old` from matching `src/backend`.

An out-of-scope action is authorized only when its referenced deviation is approved before the action and its approved prefix covers the action target. Missing, pending, rejected, late, or mismatched deviations leave the scope finding suspected. Actions with no scope policy are a visible `scope-policy-missing` rule error rather than an inferred violation.

### Missing evidence

Each requirement must have at least one admitted submission. Missing or exclusively non-admitted submissions create a suspected finding with requirement and submission facts. A submission referencing an unknown requirement is a rule error, because the engine cannot safely decide what requirement it satisfies.

### Unapproved deviation

An out-of-base-scope action that claims a deviation is compliant only when that exact deviation was approved before the action and covers its path. Missing, pending, rejected, late, or path-mismatched decisions create a suspected finding. An in-scope action does not require a deviation.

### Review order

The valid v1 order is:

`SendToLeader → LeaderDecision → EscalateToProjectManager → ProjectManagerDecision`

An out-of-order observation creates a suspected finding and does not advance the state machine. Duplicate review sequences and time regression are visible rule errors, because the order cannot be trusted.

## Explainability and duplicate suppression

Every finding records:

- finding identity;
- state `Suspected`;
- rule ID, rule version, kind, and severity;
- Task, actor, and stable subject;
- sorted supporting facts with source input IDs; and
- an explainability SHA-256 over the complete finding and facts.

The stable finding identity binds rule ID/version/kind, Task, actor, and case-insensitive subject. Repeated detections of the same condition therefore produce the same identity. The engine accepts the caller's bounded active identity set and reports each repeat as `DuplicateSuppressed`; it never silently evicts or rewrites the caller's incident state. A changed rule version, Task, actor, or subject requires a distinct identity.

Evaluation request, known-finding set, explainability, rule set, and complete result each receive separate domain-separated SHA-256 values. Input collection order cannot change the normalized request or result hash.

## Deterministic product corpus

Run the committed corpus through the built product command:

```powershell
dotnet HerdrOps.Core.dll compliance-rule-corpus `
  --input compliance-rule-corpus.json `
  --report compliance-rule-report.json
```

The command accepts strict camel-case JSON, rejects duplicate/unknown properties and numeric enum values, limits input to 8 MiB, limits cases to 64 and repeats to 4, and atomically replaces the report only after every declared expectation passes. Input and report paths must differ.
