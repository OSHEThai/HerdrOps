# v0.5 Role-distinct Compliance Review Workflow Contract — Issue #27

Status: final implementation contract; actual role-distinct Herdr runtime acceptance pending

## Purpose and evidence boundary

This contract routes a registered compliance incident through Project Manager and Leader decisions without allowing presentation state to grant authority. The implementation provides Contract, BuiltProcess Integration, local SQLite Integration, and Synthetic UI evidence. It does not by itself prove that a reviewer identity belongs to an actual running Herdr Agent, that real incident ingestion is complete, or that v0.5 is ready for release.

Static, Contract, BuiltProcess Integration, local SQLite Integration, Synthetic UI, Runtime, Independent Review, and Release evidence remain separate. The implementation gate for this contract must report `NoRuntimeCredit`; Issue #27 remains open until a fresh role-distinct runtime trace and immutable audit record are accepted.

## Canonical states and decisions

The workflow contract version is `1`.

| Current state | Authoritative role | Decision | Result state |
|---|---|---|---|
| `Suspected` | Project Manager | `Confirm` | `Confirmed` |
| `Suspected` | Project Manager | `SendToLeader` | `PendingLeader` |
| `Suspected` | Project Manager | `Dismiss` | `Dismissed` |
| `PendingLeader` | Leader | `EscalateToProjectManager` | `PendingProjectManager` |
| `PendingProjectManager` | Project Manager | `Confirm` | `Confirmed` |
| `PendingProjectManager` | Project Manager | `SendToLeader` | `PendingLeader` |
| `PendingProjectManager` | Project Manager | `Dismiss` | `Dismissed` |

Every other role, state, or decision tuple fails closed. `Confirmed` and `Dismissed` are terminal under this contract.

## Authorization, concurrency, and identity

- The review command carries a non-empty immutable command ID, incident ID, `ExpectedState`, `ExpectedSequence`, reviewer actor ID, decision, reason, and a canonical evidence-identity set. The App and CLI command payloads do not carry `OccurredUtc`.
- Core never accepts the Compliance Queue viewer role or button metadata as authority.
- Core assigns the command occurrence time with its injected `TimeProvider` when the command reaches the workflow service. The resulting Core timestamp is recorded in the immutable audit event and incident projection. `ObservedUtc` on a capability query is a client observation time, not a command occurrence time.
- Core resolves the reviewer's current assignment role from `assignment_current_actor_roles`, validates the linked lifecycle provenance event, and requires that the projection represents the latest immutable observation in `assignment_actor_role_history`.
- Only exact `Project Manager` and the explicit Leader-role allowlist map to review authority.
- `ExpectedState` and `ExpectedSequence` are one optimistic-concurrency precondition. Core reads the current incident, compares both values, validates the decision, inserts the audit event, links evidence, and advances the incident projection inside one immediate SQLite transaction. A concurrent writer cannot make either precondition stale between authorization and mutation.
- The current-role projection is guarded: its insert and update must match the latest immutable role observation, and delete is rejected. The review-event trigger repeats the current-role, latest-history, provenance, and role-allowlist checks.
- The incident subject cannot review the same incident.
- A command whose expected state or expected sequence differs from the current incident is rejected as stale.
- A Core-assigned occurrence time before the authority acceptance time is rejected.
- The CLI dispatcher routes `review` to `ComplianceReviewCliCommand` before the self-report command parser. Review JSON does not accept `reviewerActorId` or `OccurredUtc`; the CLI derives the reviewer actor ID from `HERDR_PANE_ID` and requires `HERDR_ENV=1`. Strict input rejects attempted identity or timestamp fields.
- The public CLI has no review-pipe override. Production App and CLI clients use only the deterministic current-user pipe name.
- After connecting, both production App and CLI clients obtain the OS-reported named-pipe server PID with `GetNamedPipeServerProcessId`. They validate the connected process as `HerdrOps.Core.exe` with `OriginalFilename=HerdrOps.Core.dll`, `ProductName=HerdrOps.Core`, a computed executable SHA-256, stable process start time, stable file length and last-write time across hashing, and a file timestamp no newer than process start. An exited process or changed file fails closed.
- For every capability query and mutation, the server obtains the connected client's actual Windows process ID with `GetNamedPipeClientProcessId`. It then asks the already-admitted, exact-hash Herdr connection for the claimed pane's shell and foreground process identities. The client process must be one of those processes or a Windows descendant of one of them.
- Windows authorization holds limited-information process handles for every process in the candidate-to-root chain, obtains each creation time with `GetProcessTimes`, and confirms each held process remains running. While every chain identity is still held, it recaptures the parent relationships and requires them to match the originally traversed chain. Every parent creation time must be strictly earlier than its child creation time. Inaccessible, exited, reused, reparented, unstable, cyclic, incomplete, equal-time, time-inverted, or over-depth chains fail closed.
- Process-to-pane attestation happens before Core reads capabilities or executes a command. Core still resolves current assignment authority again in the same SQLite transaction as the mutation; a process match cannot grant a role.
- The only server constructor without the capability and process-authorizer delegates is internal and exists for bounded transport rejection tests. Production Core wiring must use the fully attested constructor.

The Named Pipe is limited to the current Windows user and validates a matching App/App or CLI/CLI handshake source pair. Each client has a bounded handshake-frame deadline. One operation deadline starts before the operation frame is read and then spans client-process authorization, capability or mutation execution, and the response write; it is never reset between those phases. The server defaults both deadlines to five seconds, bounds the client count, and releases a stalled client slot. Client cancellation remains available to cancel transport before a response. These controls prevent cross-user access, source switching, and indefinite idle connections after the handshake.

The server PID, executable metadata, executable hash, process start, file-stability checks, and ancestry checks establish operational identity continuity and correlation only. They are not cryptographic publisher authentication, code-signing proof, or cryptographic process provenance. A sufficiently privileged same-user process may forge parentage with `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS`; the ancestry check therefore does not prove an unforgeable parent relationship. Herdr protocol 19 reports pane root PIDs but not their creation identities, so Core can hold and revalidate the current local root processes but cannot prove that a stale Herdr-reported PID was not recycled before the authorization snapshot began. The process check rejects a simple spoofed `HERDR_PANE_ID` from an unrelated process, but it does not prove a compromised same-user Herdr descendant, replacement of trusted local binaries, direct same-user database access, or a fake server that acquires the deterministic pipe first. A deliberate same-user database writer can open its own SQLite connection and register or spoof its own SQLite validation function; that remains a trust-boundary residual. A fake response or same-user writer cannot earn runtime credit without a separately observed, simultaneously running Herdr pane, admitted assignment-role provenance, and bound Core-owned audit record.

## Immutable incident and audit records

SQLite schema v4 adds separate incident, incident-evidence, audit-event, and audit-evidence tables.

Each accepted event records:

- reviewer actor ID and authoritative Project Manager or Leader role;
- authority provenance event ID, lifecycle sequence, and SHA-256;
- decision, previous state, result state, reason, and UTC occurrence time;
- sorted evidence identities and their evidence-set SHA-256;
- incident/task/subject identity and monotonically increasing sequence;
- previous audit SHA-256 and canonical event SHA-256.

The command ID is the audit-event ID. An exact retry returns the existing immutable event; changed content under the same ID fails. If later events already advanced the incident, the retry receipt does not republish its older decision as the current decision. SQLite triggers reject ordinary update/delete operations, reject a non-next sequence or invalid transition, require the exact current assignment-role event and provenance, and advance the incident projection only from an accepted event. Incident registration stores immutable canonical `registration_json`; `compliance_review_incident_evidence_validate_insert` uses SQLite `json_each` to admit only identities declared by that registration. Reads compare the registration JSON with the normalized scalar and evidence-link projection, and an idempotent registration retry validates the complete existing review history before returning. The `compliance_review_event_evidence_validate_insert` trigger similarly requires every event evidence-link identity to be declared in immutable `audit_json`. Before writing the next sequence, Core validates the complete prior event history, including evidence links, so a tampered earlier link blocks the append. Reads replay and validate the complete hash chain against the current incident pointer.

### Core-connection audit validation

Before an audit-event insert, the Core-owned SQLite connection registers the deterministic `herdrops_review_audit_valid` validator used by the insert trigger. The validator recalculates the UTF-8 SHA-256 of `audit_json`, deserializes and domain-validates the event, and compares every persisted scalar field with the JSON/domain value: contract and identity fields, sequence, reviewer and authority provenance, decision and state values, reason, Core-assigned occurrence time, evidence-set hash, previous audit hash, and audit hash. The read path repeats the JSON hash, domain, evidence-link, scalar-column, and replay checks.

This validator is an integrity check on the Core connection, not cryptographic publisher or code-signing proof. A deliberate same-user SQLite writer can register or spoof its own function on its own connection and remains outside this trust boundary.

The v3 evidence/audit foundation remains intact and migrates forward to v4 through the existing integrity check, migration history, and pre-upgrade backup policy.

## IPC and affected presentation state

Review commands use a dedicated current-user Named Pipe and protocol v1, separate from the read-only Herdr state stream. Frames use strict bounded JSON and a 512 KiB maximum. The server requires a valid hello source/role pair before accepting one capability query or mutation. One per-request operation deadline begins before reading the operation frame and covers that read, process authorization, capability or mutation execution, and the response write without reset. Synchronous delegate invocation is isolated on the default scheduler behind a bounded concurrency budget of four; a timed-out delegate keeps its permit and operation cancellation source until it actually completes, and its late fault is observed. Server shutdown waits for every tracked detached delegate before reporting completion, preventing dependent state from being disposed underneath surviving work. Workflow and compliance-store monitor waits recheck cancellation in bounded intervals. Compliance SQLite commands use a one-second command, provider, and `PRAGMA busy_timeout` lock-wait ceiling and register the operation token to request `SqliteCommand.Cancel`; provider failures become structured Core-unavailable responses. The cancellation request is cooperative and does not guarantee immediate interruption of a provider busy wait. Transaction acquisition and a synchronous mutation already executing inside SQLite cannot be promised immediate cancellation or rollback, so the bounded delegate permit remains occupied until that work exits.

App and CLI clients create fresh linked deadlines for connect plus server-process validation, handshake, and operation phases. No hello is sent before server-process validation succeeds. Synchronous validators run as isolated long-running tasks behind process-wide budgets of four in the App and two in the CLI. Waiting for a validator permit consumes the same validation-phase deadline; a validator keeps its permit until it actually finishes, and its late fault is observed. The client call therefore remains bounded, although an underlying validator cannot be force-cancelled and may retain its worker and pipe reference until completion. An internal phase deadline becomes `TimeoutException`; caller cancellation remains `OperationCanceledException`.

Core exposes an authoritative capability query for the selected incident and reviewer. Live review buttons remain disabled until Core confirms the exact current incident state, incident sequence, current reviewer role, and allowed decisions; a non-empty reason is also required. Clicking a live action sends both expected concurrency values to Core, where the same checks are repeated transactionally.

The App uses capability and command request generations, a per-incident authoritative generation, selected-incident identity, expected state and sequence, an atomic single-flight command guard, pending-command, and disposal guards. A capability result is applied only when its generation, selection, and sequence are still current. Any different authoritative same-incident replacement or sequence advance increments the incident generation and invalidates an older in-flight command. A late accepted result is recognized only when it produced the exact next incident generation and the incident's last audit-event ID equals that command ID. Rejected results are never published into shared authoritative state, and a late rejection cannot overwrite status after the same incident changes. Disposing the Queue invalidates outstanding generations, and selection accepts only a visible incident.

Core returns the authoritative incident snapshot and immutable audit event only for an accepted result. Before publication, the App coordinator binds the result to the originating request: the incident ID must match, and an accepted result must carry the request command ID as its audit-event ID plus the exact reviewer, decision, previous state, next sequence, reason, evidence identities, task, subject, result state, and audit-hash linkage. An exact already-present retry may return a later current incident, but its immutable request-bound audit event is not presented as that later incident's current decision. Rejected results carry status, code, and message only; they carry no incident snapshot and are not published into shared authoritative state because the request does not carry enough immutable registration data to bind a snapshot safely. The coordinator validates both Domain contracts before publishing accepted state through one shared review-state hub. Once an accepted response containing an authoritative incident is received, the coordinator publishes through the UI dispatcher with caller cancellation excluded from the publication step; caller cancellation can still cancel transport before a response. The StateHub invokes subscribers independently: a nonfatal subscriber failure is logged with its exception type only, later subscribers still receive the accepted change, and the same immutable state is not replayed twice. Immutable registration conflicts, sequence rollback, and conflicting state at one sequence fail closed.

The Queue consumes the hub event as the authoritative live projection. The Widget consumes that same event and creates a localized review notice with route `compliance-review:{incidentId}`. The application widget router selects that incident, navigates to `compliance-queue`, and activates the main window; it fails closed if the exact incident or target window is unavailable. Live status messages remain polite, localized, and non-authoritative for pending, ready, accepted, already-accepted, canceled, stale, unauthorized, and unavailable outcomes. Dispatcher scheduling keeps WPF-bound updates on the UI thread.

The Issue #26 deterministic screenshot fixture remains read-only. Its four buttons remain disabled and do not become authorization evidence. Live incident source completeness, reconnect replay, privacy, and retention acceptance remain Issue #28.

## Language contract

Thai mode contains complete Thai user-facing review, rejection, queue, Widget, and live-status messages. English mode contains complete English equivalents. Only one selected language is rendered at a time. Actor IDs, incident IDs, task IDs, protocol names, route values, and hashes remain technical identifiers and are not translated.
