# v0.3 Activity Event Pipeline Contract — Issue #12

Status: implementation and automated evidence complete; independent review found no actionable P0-P3 issues; clean-checkout gate pending

## Purpose and boundary

This contract establishes the deterministic activity foundation consumed by later v0.3 collectors and user interfaces. It covers normalization, local ordering, exact deduplication, explicit correlation, bounded debounce, source-sequence observations and fixture replay.

It does not connect to an installed Herdr process, read pane output, collect Windows process metrics, watch files, inspect Git, persist activity rows or render Realtime Activity. Those capabilities remain in Issues #13 through #16 and require their own Contract, Runtime and UI evidence.

## Versioned envelope

Every accepted event uses activity contract version 1 and supplies:

- a non-blank source event ID;
- source kind, source instance and source epoch;
- a positive source sequence when the producer has one, otherwise JSON `null`;
- confidence, urgency and delivery mode enums;
- a bounded event type;
- UTC occurrence and observation timestamps;
- a non-empty correlation ID;
- an optional debounce key, Agent terminal ID, pane ID, task ID and process ID;
- an already-redacted summary of at most 1,024 characters;
- an exact 64-character payload SHA-256.

Identifiers are unpadded Unicode Form C without control characters. Summaries normalize line endings to `LF` and allow only tab and newline control characters. Enum integers, non-UTC timestamps, empty correlation IDs, non-positive supplied sequences or process IDs, malformed hashes and unmapped JSON members fail closed.

The envelope deliberately excludes raw terminal output, command lines, file content and other payload bytes. A collector must redact and bound its data before constructing the envelope.

## Canonical hashes and deduplication

The pipeline computes two SHA-256 values:

1. The identity hash binds source kind, source instance, source epoch and source event ID.
2. The envelope hash binds every normalized field.

Canonical hash input uses a domain separator, length-prefixed UTF-8 strings and fixed little-endian numeric values. JSON serialization and property order are not hash inputs.

An exact repeated identity and envelope is a duplicate and does not publish twice. The same identity with different normalized content is a conflict and is rejected. The identity cache is bounded; deterministic first-in eviction prevents unbounded memory growth.

## Ordering and source sequence

HerdrOps assigns a positive local ingest sequence in received order. That local number orders work inside one pipeline instance and does not claim that the source delivered every event.

For each `source kind + source instance + source epoch` stream:

- the first supplied source sequence establishes a baseline;
- baseline plus one advances normally;
- a larger value is accepted with an observable gap;
- a different event at the current value is a conflict and is rejected;
- a lower value is a regression and is rejected.

An event with no source sequence bypasses source-gap tracking. HerdrOps does not invent a source sequence or a gap-free claim. Source-stream tracking is bounded with deterministic first-in eviction; an evicted stream establishes a fresh observed baseline if it returns.

## Urgent and noisy delivery

High and Critical events always produce an immediate emission. This bypass applies even when the input delivery mode says Debounced, and no debounce key is required for an urgent event.

Normal Immediate events also publish individually. Normal Debounced events require a key and aggregate only when source stream, event type, correlation ID, debounce key, confidence and Agent/pane/task/process context all match. A bucket:

- opens at the first observation;
- has a fixed deadline at first observation plus the configured window;
- stores constant-size first/last metadata, count and a rolling aggregate hash;
- publishes at window expiry, deterministic capacity pressure or replay completion.

The fixed deadline prevents an endless noisy stream from postponing publication forever. Open buckets have a configured hard limit; the oldest bucket flushes first under pressure.

## Deterministic replay command

Run the committed fixture through the product command:

```powershell
dotnet HerdrOps.Core.dll activity-replay --input activity-replay.json --report replay-report.json
```

The input is strict camel-case JSON, limited to 16 MiB, with duplicate properties, unknown members and numeric enum values rejected. Input and report paths must differ. A valid report is written atomically only after the entire input and replay succeed.

The committed fixture at `tests/fixtures/v0.3/activity-replay.json` has these exact anchors:

- fixture SHA-256: `8A7276170438360238803DD057BB6FB81F2745EC888C1A9DD2CF304B824633E1`;
- replay result SHA-256: `9FC1E4E87291608DE338361E31315ABB01A73ACF4457F55EC2E263A734D3D82E`;
- complete report SHA-256: `775938CADB509FD94329B4349A35E49DB5E728F76DB1C2258F83A1ED92D1D06A`;
- 12 inputs, 11 accepted events, 1 exact duplicate and 0 rejected events;
- 1 observable source gap;
- 2 urgent inputs and 2 urgent immediate emissions;
- 11 emitted source events for 11 accepted events;
- peak cache/bucket counts at or below every configured bound.

The report declares `Synthetic` evidence and `runtimeObserved: false`. It contains no run timestamp or machine path, so repeated runs against the same exact input and implementation produce byte-identical output.
