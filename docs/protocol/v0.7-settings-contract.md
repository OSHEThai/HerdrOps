# HerdrOps v0.7 Settings Contract

Status: bounded non-runtime contract/integration slice for GitHub Issue #36.

This contract defines the versioned local settings document used for reversible
language, widget, and user-preference changes. It does not start Herdr, create a
tray icon, register startup, install a package, or prove reference-host
accessibility.

## Evidence boundary

- Contract: model, version, field vocabulary, validation, canonical JSON, path
  policy, best-effort reparse-point rejection, cleanup semantics, and fail-closed rules.
- Integration: local JSON read/write, restore, reset, and atomic replacement
  tests using a temporary directory.
- Synthetic: injected commit failures, post-publication failures, concurrent
  saves, cancellation, artifact collisions, and cleanup/rollback ordering
  prove the bounded persistence semantics while the previous admitted file
  remains unchanged.
- Actual Herdr Runtime: NOT OBSERVED.
- Reference-host accessibility: NOT OBSERVED.
- Release: NOT OBSERVED.

## Canonical document

The current schema is version `1`. The document is strict UTF-8 without a BOM,
has a maximum encoded size of 16 KiB, uses the exact property set below, and is
serialized with stable camel-case property order and a final newline.

```json
{
  "schemaVersion": 1,
  "language": "th",
  "widgetVariant": "normal",
  "widgetEnabled": true,
  "widgetPinned": false,
  "userPreferences": {
    "selectedProjectId": null,
    "showOfflineAgents": true,
    "reducedMotion": false,
    "refreshIntervalSeconds": 5
  },
  "localExportDirectory": null
}
```

The default language is Thai and the document stores one language selection at
a time: `th` or `en`. It never stores Thai and English product labels together.
Product names, Agent names, identifiers, paths, and protocol values remain
literal values owned by their relevant contracts. This settings document has no
secret, token, password, API-key, or connection-credential field.

The seven allowed widget values are `compact`, `normal`, `expanded`,
`floating-mini`, `floating-vertical`, `notification`, and
`agent-detail-popup`.

## Validation and fail-closed behavior

Admission rejects:

- unknown schema versions, missing or duplicate properties, unknown properties,
  malformed JSON, comments, trailing commas, invalid UTF-8, UTF-8 BOMs, and
  non-boolean or non-integer primitive values;
- unsupported language/widget values, invalid refresh intervals, control or
  unbounded project identifiers, and invalid destination values;
- documents larger than 16 KiB encoded UTF-8;
- relative, traversal-containing, UNC, device-relative, device-namespace,
  filesystem-root, empty-filename, trailing-separator, reserved-device-name,
  alternate-data-stream, invalid-character, or out-of-allowed-root destinations;
- any existing reparse-point component observed during the deterministic
  best-effort path checks, including the allowed root, destination directory
  ancestry, and an existing destination file.

An invalid document is never converted into defaults and never overwrites the
last valid file. A failed save leaves the previous destination unchanged. Save
operations are serialized per normalized destination within the process, so a
rollback cannot remove or replace a later save for the same destination. A
temporary file and, when needed, a backup are created beside the destination,
flushed to disk, atomically replaced/moved, and cleaned up with an explicit
outcome. Artifact ownership is recorded only after the corresponding
`CreateNew` succeeds; a collision therefore never authorizes deletion of an
artifact created by another operation. Cleanup is attempted from recorded
ownership rather than an existence probe, so inaccessible or ambiguous
artifacts produce a visible cleanup failure.

If the primary commit operation and cleanup both fail, the store throws an
`AggregateException` whose first inner exception is the primary commit
exception and whose second inner exception is the cleanup exception. If the
commit succeeds but cleanup fails, the store throws `SettingsValidationException`
with the cleanup exception as its inner exception; the destination may already
contain the new canonical document in that case. Cleanup failures are never
silently ignored.

Cancellation is checked before settings validation, serialization, snapshot
integrity validation, and document parsing. Cancellation during file I/O is
also propagated. The store checks cancellation immediately after invoking the
atomic commit. If any exception is observed after the commit invocation,
including a non-cancellation exception thrown after publication, it attempts to
restore the previous destination (or remove the new file when no previous
destination existed). Cancellation is rethrown only after rollback and cleanup
succeed. If rollback or cleanup cannot be completed, the store throws an
explicit validation error describing the uncertain outcome.

`localExportDirectory`, when present, must be a local absolute non-root path.
Callers may additionally require it to be contained by an approved local root.
The policy accepts a destination directory equal to the approved local root,
rejects traversal segments before normalization, and performs deterministic
best-effort rejection if an existing path component is a reparse point. It is
not a handle-relative/no-follow boundary and does not claim to prevent a
concurrent same-user reparse-point swap. Callers requiring adversarial
containment must supply a Windows handle-based no-follow policy separately. It
is intentionally separate from any future installer or runtime policy.

## Reversal contract

`SaveAsync` returns an admitted `AppSettingsSnapshot` containing the immutable
settings value, canonical JSON, and SHA-256 digest. `RestoreAsync` recomputes
both canonical JSON and digest before writing; a tampered snapshot is rejected.
`LoadAsync` parses valid input into an admitted settings value and returns a
snapshot containing the deterministic canonical JSON and digest, even when the
file that was read used valid but non-canonical whitespace or property order.
Loading does not rewrite that file; `RestoreAsync` or `SaveAsync` writes the
canonical bytes.
`ResetToDefaultsAsync` writes the explicit defaults shown above. Therefore a
language/widget/user-preference change can be reversed to a previously admitted
snapshot or reset without relying on a mutable in-memory fallback.

No test in this slice claims Herdr Runtime, tray, startup, installer, or
reference-host accessibility evidence.
