## Purpose and presentation boundary

This contract defines the v0.6 Evaluation presentation surface. It consumes the
`HERDROPS-EVALUATION-V1` result and provenance model from the explainable scoring
contract; it does not replace the scoring formula, admit production evidence, or
authorize a review decision. The approved page preserves the shared HerdrOps shell:
brand mark and wordmark, top project/status bar, left navigation, content workspace,
and bottom connection/status bar.

## Approved hierarchy

The content workspace presents the following synchronized hierarchy, in this order:

1. Five summary cards:
   - Average Score Today
   - Total Evaluations
   - Leader Reviews Pending
   - PM Reviews Pending
   - Recurring Issues
2. Score Distribution: five fixed bands, `90–100`, `75–89`, `60–74`, `40–59`, and
   `0–39`, with counts and percentages.
3. Score Trend: seven daily points for the selected seven-day window, with the
   displayed date and value for every point.
4. Dimension Breakdown: Goal Alignment (20%), Acceptance Criteria (20%), Technical
   Quality (20%), Scope Compliance (15%), Evidence (15%), and Communication (10%).
5. Selected Task/Agent source comparison: the selected literal Task and Agent, the
   Leader score, Project Manager score, Objective Evidence score, and each dimension's
   weighted contribution.
6. Top Performing Agents and Low Performing Agents, with rank, literal Agent
   identity, score, and change where available.

The hierarchy must remain understandable at the reference viewport and at the
minimum supported desktop viewport. Selection, filtering, and the seven-day window
may change the selected presentation state, but every visible region must remain
synchronized to the same state.

## Immutable presentation snapshot

One immutable, normalized presentation snapshot is the sole value source for every
card, chart, dimension row, selected comparison row, ranking, unresolved-data marker,
and provenance reference in a render. The snapshot binds the evaluation result,
formula, input snapshot, source slots, provenance identities, evidence identities,
selection, time window, and result hashes supplied by the scoring contract.

Cards, charts, tables, and rankings must not fetch, recalculate, round, or repair
values independently. A language change re-renders labels from the same snapshot;
it does not create a second value source. A changed Task/Agent selection creates a
new complete immutable snapshot rather than mutating the snapshot already rendered.

## Missing, invalid, and deterministic values

Missing and invalid scores are visible as explicit `Missing`, `Invalid`, `Incomplete`,
or `Unknown` states with their reason and affected source or dimension. They fail
closed: the UI never substitutes zero, places an unresolved record in the `0–39`
band, presents a partial total as a passing score, silently drops the record, or
uses an invalid value in an average, trend, contribution, or ranking. Numeric
aggregates expose their eligible denominator and unresolved count; when no complete
value exists, the numeric result is null/Unknown. Unavailable evidence remains
visible with its provenance and availability state.

Only complete values participate in numeric ranking and numeric chart series. An
unresolved identity remains visible in the selected comparison or an explicit
unresolved section, but receives no fabricated rank. The presentation preserves the
scoring contract's null total and `AvailableWeightBasisPoints` semantics.

All ordering is deterministic and independent of display language or locale. Numeric
ties are resolved by ordinal comparison of stable technical keys in this order:
`AgentId`, `TaskId`, then `EvaluationId`; missing keys remain unresolved rather than
being replaced by display labels. Date buckets use the normalized UTC day and a
stable evaluation key. Repeated equal input snapshots therefore produce identical
cards, charts, rows, ranks, and textual equivalents.

## Language and literal-data rules

Thai and English are separate complete presentation modes. A rendered surface uses
exactly one selected language: Thai mode does not stack English translations, and
English mode does not stack Thai translations. Card titles, chart labels, legends,
empty/error explanations, tooltips, accessibility text, and automation names all
come from the selected catalog.

Product names, Herdr/Agent names, Task names and IDs, evaluation IDs, identifiers,
paths, hashes, protocol values, and other technical source data remain literal. They
are not translated, transliterated, or replaced by localized aliases. Language
switching changes presentation copy only and never changes snapshot values, sort
keys, provenance identities, or evidence hashes.

## Accessibility and automation

Charts must have visible labels and a non-color textual equivalent. The distribution
equivalent lists every fixed band, count, percentage, and unresolved count. The trend
equivalent lists all seven normalized dates and values or the explicit unavailable
reason. The dimension equivalent exposes each dimension, weight, score, contribution,
and unresolved state. The source comparison and top/low performer regions remain
readable as tables or ordered text, including rank, score, change, source, and
provenance state.

Every card, chart, legend item, selector, selected comparison region, dimension row,
performer row, provenance link, and unresolved-state control has a non-empty,
distinct automation name and relevant help text in the selected language. Labels,
status text, icons, and patterns supplement color; color is never the only signal.
Keyboard focus, readable contrast, control state, and the selected row are visible
and exposed to UI Automation. Technical identifiers in automation text remain
literal under both language modes.

## Evidence and provenance

Each displayed source score links to its source boundary and provenance identity:
Leader, Project Manager, or Objective Evidence. Where supplied, the presentation
also exposes the evidence identity SHA-256, availability, bounded reference/path,
and the evidence/result hash that binds it to the immutable snapshot. A missing
artifact is shown as explicit Missing metadata; the UI does not invent bytes,
provenance, authorization, or a successful score.

The presentation may link to admitted source metadata and evidence records, but it
does not rewrite them, merge role sources, treat a Leader or Project Manager value
as objective evidence, or infer production evidence admission. The selected Task,
Agent, source slot, dimension, score, contribution, and displayed provenance must
remain traceable to the same snapshot and retained formula/input hashes.

## Evidence classes and non-claims

- **Static:** contract text, reference identity/hash, source shape, formula/display
  token, language-catalog, and accessibility/automation checks.
- **Synthetic:** deterministic snapshots, fixtures, replay data, and WPF captures
  rendered from non-live data.
- **Contract:** scoring-schema, snapshot-hash, source/provenance, fail-closed,
  language-mode, accessibility, and automation compatibility checks.
- **Runtime:** observation against an actual installed Herdr instance, including
  its live connection and data; this contract provides no Runtime evidence.
- **Independent Review:** a separate authorized review of the implementation and
  evidence; it is not supplied by this contract.
- **Release:** packaged artifact, clean-machine installation, runtime acceptance,
  required approvals, and release-gate results; none are supplied here.

Static, Synthetic, and Contract results must be reported separately. Runtime,
Independent Review, and Release remain separate evidence classes and cannot be
inferred from a green checker, a synthetic capture, a replay, or this contract.
Actual Herdr Runtime is not proved here.
