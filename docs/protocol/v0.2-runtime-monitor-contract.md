## Admitted predecessor contracts

The runtime client starts only after both predecessor inspections bind to the same executable:

- Herdr release: `0.8.0-preview.2026-08-04-d78e3d3b5126-x86_64-pc-windows-msvc`
- Executable SHA-256: `6F470DA358D6713B6BEBAB922FFB1F5FE1D3D288CC6F374C7DCA1B4A9837A542`
- Bundled schema SHA-256: `9449368D54BBECD4D4D0696EFFB9E9C002ECD63A5B8A48BBD901A305AF842982`
- Protocol: `19`

Any identity, path, hash, schema, or live snapshot protocol mismatch fails closed before state is
accepted. The client does not invoke the Herdr CLI or a session-control method.

After each pipe connection, HerdrOps asks Windows for the Named Pipe server PID, resolves that
process image, reads the image through a handle-bound snapshot, and requires its SHA-256 to equal
the admitted Herdr executable. A protocol-compatible synthetic pipe served by another process
cannot earn Runtime credit. The verified PID, process start time, resolved image path, and hash are
retained for every connected bootstrap in the trace. Discovery, subscription, and authoritative
snapshot connections within one bootstrap must all resolve to the same PID/start/path/hash tuple;
a process change during bootstrap fails closed and starts a fresh epoch.

## Wire contract

Static source embedded in the admitted executable writes one UTF-8 JSON request followed by `LF`
to the Windows Named Pipe. The binary also contains the server diagnostics `api request line is too
large` and `timed out reading api request`. HerdrOps therefore uses bounded newline-delimited JSON
for both request/response and subscription frames.

- Endpoint source order: explicit path, `HERDR_SOCKET_PATH`, then the current-user default
  `%APPDATA%\herdr\herdr.sock`.
- Windows pipe prefix: `\\.\pipe\`; the .NET client receives the logical pipe name without that
  prefix.
- Maximum inbound or outbound JSON line: 4 MiB.
- Encoding: strict UTF-8 without accepting malformed byte sequences.
- Request correlation: every response `id` must exactly equal the request `id`.
- Snapshot request: `session.snapshot` with an empty `params` object.
- Subscription request: `events.subscribe` with exactly one
  `pane.agent_status_changed` filter for each unique pane found by the discovery snapshot and no
  general-event subscriptions. Each entry supplies `pane_id` but deliberately omits the optional
  `agent_status` selector.
- Subscription acknowledgement: `subscription_started` must precede event frames.

The exact admitted Herdr source retains at most 512 general events and initializes each new
general-event subscription cursor at sequence zero. A newly acknowledged general subscription
therefore replays retained process history before it reaches live events. The wire envelope does
not expose that server sequence, so neither a frame count nor a quiet interval can prove a
replay/live boundary. HerdrOps does not subscribe to that stream. In the same admitted source, a
pane-filtered `pane.agent_status_changed` subscription starts at the event hub's current sequence;
those filtered frames are the monitor's only live Event source. In that source, an initial matching
status frame is created only when the optional `agent_status` selector is present. HerdrOps omits
the selector, so subscription setup cannot invent an Event count.

Malformed JSON, an empty or partial line, oversized data, unknown agent status, response-ID
mismatch, API error, stream termination, and unknown state-changing event all abandon the current
stream and require a fresh snapshot.

If a caller cancels while a partial frame is buffered, the reader retains those bytes for a later
read on the same live subscription. Disposing the subscription still closes the pipe and abandons
the partial frame.

## Bootstrap and reconciliation

Each connection epoch performs the following sequence:

1. Read a discovery snapshot to obtain the current pane filter set.
2. Open and acknowledge the pane-filtered live Agent-status subscription.
3. Read a second authoritative snapshot while that subscription remains active.
4. Replace the complete in-memory workspace, tab, pane, and agent dictionaries.
5. After each observed live status frame, read and validate a following authoritative snapshot
   before publishing changed status/topology content; the frame alone increments Event count.
   If that snapshot fails, retain the last authoritative content, preserve the consumed frame's
   local sequence and Event count, and enter Reconnecting.
6. Poll an authoritative snapshot every second for topology and metadata changes. An unchanged
   poll advances no sequence or counter, and a changed poll increments reconciliation but not
   Event count. Before the poll, cancel and await the active subscription read. A frame that wins
   that cancellation race is processed first; otherwise no read remains active while the poll can
   decide to refresh pane filters.
7. If the authoritative pane set changes, publish the complete state and start a new filtered
   subscription epoch.

The second snapshot closes the snapshot-before-subscribe race. Fetching another snapshot after an
observed status frame avoids assigning unsupported ordering semantics to a payload that carries no
server sequence. A pane create, close, or move is discovered by authoritative polling and rebuilds
the pane-specific filters through a new epoch. Workspace, tab, pane, and Agent focus mirrors are
replaced atomically; contradictory references, counts, or focus flags fail closed.

A filtered `pane.agent_status_changed` frame for an unknown pane or mismatched workspace requests
immediate reconciliation and refreshed filters. HerdrOps never invents an Agent from a status
frame. Its consumed-frame sequence and Event count remain visible, but the reconnecting transition
has no `AcceptedEventKind` and cannot satisfy composite Event A/B evidence. A filtered frame whose
authoritative snapshot fails or changes the pane set is likewise unlabelled. Only a successfully
reconciled connected transition receives `AcceptedEventKind=pane.agent_status_changed`.
General-event parsers and reducer behavior remain defensive compatibility code and Contract
tests; they are not requested by the production subscription and cannot supply Runtime Event
credit. The monitor source-gates credit to the exact dotted event name. An underscore status name,
topology frame, or any other unexpected subscription frame advances only the consumed local
sequence, enters reconciliation, and leaves Event count unchanged.

The protocol 19 event envelope has no global sequence field. HerdrOps does not invent one. It adds
a local monotonic ingest sequence and connection epoch for ordering inside HerdrOps. Snapshot
validation preserves the Herdr `PaneInfo.revision` and Agent `state_change_seq` values. Defensive
reducer tests retain these rules for revision-bearing frames:

- revision less than current state is stale and discarded;
- revision equal to current state is duplicate unless its content conflicts;
- current revision plus one is accepted;
- a jump greater than one requests immediate reconciliation;
- disconnect, parse failure, incomplete state event, or unexpected event also requests reconciliation.

Events without a Herdr revision cannot independently prove that no server event was missed. Their
state becomes authoritative only through the snapshot/reconnect rules above.

## Current verification

Automated tests cover:

- exact snapshot and subscription request shapes;
- response-ID correlation and protocol-19 admission;
- regular underscore events and filtered dotted events;
- a real local Windows Named Pipe client/server round trip;
- strict UTF-8, partial frame, malformed frame, and 4 MiB bound behavior;
- cancellation after a split multibyte partial frame followed by a lossless resumed read;
- complete workspace/tab/pane/agent bootstrap;
- atomic two-tab/two-pane focus mirrors and fail-closed focus invariants;
- duplicate-safe reducer behavior and cascading close handlers;
- a subscription request containing only unique pane-filtered live status entries;
- exact dotted-name Event credit and zero credit for underscore/general subscription frames;
- repeated live status observations reconciled by following snapshots without a resubscription loop;
- consumed live status retained when its following snapshot fails;
- periodic authoritative refresh without invented Event count;
- deterministic read-barrier handling when an Event and topology poll race;
- periodic pane-set change followed by refreshed pane filters;
- no incomplete Connected bootstrap when discovery and authoritative pane sets differ;
- single-run enforcement and subscription disposal before reconnect backoff;
- forced synthetic disconnect followed by fresh state replacement;
- stale queued pane events discarded after the authoritative snapshot;
- pane revision gap followed by fresh snapshot reconciliation;
- cross-workspace `pane_moved` reconciliation, corrected counts, and resubscription;
- a real Windows pipe round trip using the PID/start/path/hash verifier;
- reconnect backoff bounded at 2 seconds.

These results are Synthetic and Contract evidence. They do not prove communication with an actual
Herdr process.

## Actual runtime gate

The preferred release-facing gate combines the exact-Herdr Core trace with production WPF pages,
live Widgets, Dashboard-close continuity, state-hash correspondence, idle resources, latency,
non-elevated execution, and owned-listener checks:

```powershell
$targetAgentLabSocket = Join-Path $env:APPDATA 'herdr\herdr.sock'
./tools/Test-V02LiveRuntimeAcceptance.ps1 `
    -TargetHerdrSocketPath $targetAgentLabSocket `
    -Language Thai `
    -DurationSeconds 600
```

Run the command from a fresh, unmoved, non-elevated pane in the dedicated `acceptance` Named Session. Its
`HERDR_SOCKET_PATH` is the control socket that keeps the gate alive. The supplied target path is the
different `default` Agent Lab socket. Matching control and target sockets or observed server
PID/start identities fail closed because a full server stop terminates every pane process in that
session. Accepted transitions must occur in this order: Event A, target transport disconnect,
replacement target PID/start plus a connected snapshot, then Event B from the replacement process.
Each Event phase admits one of two bounded orderings: a direct one-step Event transition, or exactly
one unlabelled connected snapshot reconciliation followed by the Event transition. The second form
accounts for the installed runtime race in which the one-second snapshot observes the new Agent
status immediately before the buffered subscription frame arrives. Both forms require exactly one
Event-count increment, an unchanged connection epoch plus bootstrap/disconnect counters, no more
than one reconciliation for each admitted sequence, at least one same-Agent/same-pane status change,
and a matching Core transition whose `AcceptedEventKind` is exact
`pane.agent_status_changed`. The Core report also binds the accepted frame's workspace, pane and
status to that App-observed Agent change. Extra sequences, extra Events, labelled leading snapshots,
topology changes, and unrelated-pane status changes fail closed.
After Event B, the App records every reset while it waits for five continuous seconds of an unchanged
runtime fingerprint: Core-connected/live flags, runtime status and timestamps, connection epoch,
state sequence, bootstrap/Event/disconnect/reconciliation counters, and normalized state SHA-256.
It starts the timed idle sample only after that quiescence window; later Events are never filtered,
subtracted, or converted into idle evidence. Each phase record is appended to a SHA-256-chained JSONL
history so independent acceptance can reject deletion, reordering, or phase substitution.

When the Dashboard closes and a Widget remains visible, the production App releases the Dashboard
visual tree, retains only the selected Widget surface, releases capture buffers, and performs managed
large-object-heap cleanup before measurement. Weak references must show every tracked rendered bitmap
is no longer reachable before cleanup can pass. It never invokes a native working-set trim. The report
preserves before/after working set, private memory, managed heap, process identity, full start/finish
runtime fingerprints, the first observed fingerprint change, and every 250 ms resource sample. Core
verifies server images with streaming SHA-256 reads and does not retain an executable-sized image
after admission. These lifecycle operations do not waive the combined 180 MB maximum working-set
target.
